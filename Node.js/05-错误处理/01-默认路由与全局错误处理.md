# 默认路由与全局错误处理中间件

> [!abstract] 本篇定位
> 错误处理板块开篇（#90–#92）。此前每个控制器都在复制粘贴 try/catch（[[04-Mongoose实战/02-MVC架构与Express实现CRUD|见样板代码的吐槽]]）——本篇建立错误处理的骨架：**未匹配路由 → 统一 404；所有 throw/error → 一个全局中间件**。

## 一、错误分两类（#91 的理论根基）

![Operation vs Programming Errors](img/course-err01-error-types.jpg)
*图 E1-01 · 视频 #91 · 操作错误 vs 编程错误对照幻灯片*

| | 操作错误 (Operational) | 编程错误 (Programming) |
| :--- | :--- | :--- |
| 性质 | 可预期、运行时条件问题 | 代码 bug |
| 例子 | 找不到记录、URL 打错、连不上库、请求体非法 | 读 undefined 属性、传错参数类型、把 string 当 number |
| 对策 | 优雅响应给用户（400/404…） | 崩溃重启 + 记日志排查 |

> [!important] 这个分类决定后面所有设计
> 操作错误要**分类响应**（[[05-错误处理/03-开发与生产错误与常见错误类型]]）；编程错误宁可让进程崩掉由进程管理器重启，也不能带病运行。

## 二、兜底路由：处理"不存在的路径"（#90）

![404 default route 现场](img/course-err01-default-route.jpg)
*图 E1-02 · 视频 #90 · 请求不存在的 /genres 时 Postman 收到的错误响应*

Express 路由**自上而下**匹配，全都不匹配时需要显式兜底：

```javascript
// app.js —— 注意位置：必须在所有业务路由【之后】
app.all('*', (req, res, next) => {                 // all = 任何 HTTP 方法
  // next(参数) —— 只要有实参，Express 就视为【错误】，跳过其余中间件直达错误处理器
  next(new AppError(`Can't find ${req.originalUrl} on the server!`, 404));
});
```

## 三、自定义错误类 `AppError`（#92）

![AppError 类代码](img/course-err02-apperror.jpg)
*图 E1-03 · 视频 #92 · utils/AppError.js：extends Error + statusCode*

```javascript
// utils/AppError.js
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);                                  // 把 message 交给基类
    this.statusCode = statusCode;
    this.status   = `${statusCode}`.startsWith('4') ? 'fail' : 'error';
    this.isOperational = true;                       // 标记为"操作错误"

    Error.captureStackTrace(this, this.constructor); // 干净的堆栈（不包含构造调用帧）
  }
}
module.exports = AppError;
```

> [!tip] 为什么不直接 `new Error()`
> 裸 Error 没有 `statusCode`，全局处理器只能猜 500。`AppError` 让错误**自带 HTTP 语义**，处处 `next(new AppError(msg, 404))` 即可。

## 四、全局错误处理中间件（#91）

![全局错误处理中间件代码](img/course-err01-global-handler.jpg)
*图 E1-04 · 视频 #91 · 四参数中间件签名 (err, req, res, next) 与最小实现*

```javascript
// app.js —— 位置：所有路由（含兜底路由）之后
app.use((err, req, res, next) => {          // 4 个参数 = Express 唯一认识的"错误中间件"
  err.statusCode = err.statusCode || 500;
  err.status    = err.status    || 'error';

  res.status(err.statusCode).json({
    status: err.status,
    message: err.message,
  });
});
```

> [!important] 错误如何"流"到这个中间件
> 1. 同步 `throw` / `next(err)` → 直达错误中间件
> 2. **异步 Promise reject** → 默认直接崩进程（Express 4），需要包装，见 [[05-错误处理/02-异步错误处理与NotFound|下一篇 catchAsync]]
> 3. 兜底路由 `next(new AppError(...))` → 同样到达这里
> 官方文档：[Express Error Handling](https://expressjs.com/en/guide/error-handling.html)

## 五、骨架总览

```text
请求 ─► 路由中间件 ─► 控制器(可能 throw / next(err))
                          │
   ┌──────────────────────┤
   ▼                      ▼
匹配失败 → 兜底路由        同步错误
app.all('*') → next(AppError)    │
   └──────────────► 全局错误中间件 ◄┘
                     res.json({status, message})
```
