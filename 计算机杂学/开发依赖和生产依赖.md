

> [!abstract] 一句话
> `dependencies`（生产依赖）是==项目跑起来==必须有的包；`devDependencies`（开发依赖）是==只在写代码、构建、测试时==用的包，**上线运行不需要**。分清它们，团队装依赖才快、部署镜像才小、CI 才不会装一堆用不上的东西。
> 相关：[[npm和npx有什么区别]]

---

## 一、为什么 npm 要把它们分开

一个项目里有两类包，命运完全不同：

- **运行时离不开的**——比如 Express 项目的 `express`、React 项目的 `react`。没有它们，应用根本跑不起来。
- **只在"造"的过程中用的**——比如 `typescript`（编译成 JS 后就没它的事了）、`eslint`（写代码时检查）、`jest`（跑测试）。**产物里没有它们，运行时也用不到。**

npm 用 `package.json` 里的**两个字段**把这两类账分开记，从而让"装依赖"这件事可以按需裁剪：

```text
npm install
   │
   ├─ 完整安装（本地开发）：dependencies + devDependencies 全装
   │
   └─ npm install --production（或 NODE_ENV=production）
        └─ 只装 dependencies ──▶ 部署机器 / Docker 镜像 / 服务器
```

> [!tip] 一句话判断放哪个
> 问自己：==**"编译/打包完的产物，运行时还 import 得到它吗？"**==
> import 得到 → `dependencies`；只在编译、检查、测试阶段用 → `devDependencies`。

## 二、两个字段对照

| | `dependencies` | `devDependencies` |
| --- | --- | --- |
| **含义** | 生产依赖：运行时必需 | 开发依赖：开发/构建/测试时用 |
| **安装命令** | `npm i xxx`（默认） | `npm i -D xxx` |
| **`--production` 时** | ✅ 安装 | ❌ 跳过 |
| **别人 `npm i` 你的库时** | ✅ 会连带安装 | ❌ 不会安装（见第四节） |
| **典型例子** | express、react、vue、axios、lodash | typescript、vite、webpack、eslint、jest、tsx、@types/* |

**命令速记：**

```bash
npm i express              # 记入 dependencies      （-S / --save 是默认行为，可省）
npm i -D typescript        # 记入 devDependencies   （-D = --save-dev）
```

> [!note] 忘了 `-D` 会怎样
> 包被记进 `dependencies`，功能上**不报错**，只是账记错了：部署机器会多装一个运行时根本用不到的包。
> 改正：手动把条目挪到 `devDependencies`，或删掉重装 `npm uninstall xxx && npm i -D xxx`。

## 三、典型的项目 package.json

```jsonc
{
  "name": "my-node-app",
  "dependencies": {              // 运行时 import 的
    "express": "^4.19.2",
    "axios": "^1.7.2"
  },
  "devDependencies": {           // 只在开发/构建期用的
    "typescript": "^5.4.5",
    "tsx": "^4.11.0",
    "eslint": "^8.57.0",
    "jest": "^29.7.0",
    "@types/node": "^20.12.0"
  }
}
```

对应的项目结构树：

```text
my-node-app/
├── package.json                 ← 两本账都在这里
├── package-lock.json            ← 锁定两类依赖的精确版本
├── node_modules/                ← 完整安装时两类包【混在一个目录】
│   ├── express/                 ← 生产依赖
│   ├── axios/                   ← 生产依赖
│   ├── typescript/              ← 开发依赖
│   ├── eslint/                  ← 开发依赖
│   └── ...
├── src/
│   ├── index.ts                 ← import express / axios（生产代码用生产依赖）
│   └── index.test.ts            ← import jest 的 API（测试用开发依赖）
└── dist/                        ← 编译产物：里面【没有】typescript/eslint
```

> [!info] node_modules 里不分家
> 完整安装时两类包**混在同一个 `node_modules`**，npm 只在"裁剪安装"（`--production` / `--omit=dev`）时才跳过 devDependencies。所以看目录分不出谁是谁——**账本只认 `package.json`**。

## 四、关键细节：装"你的包"的人，不会装你的 devDependencies

这是很多教程漏讲、但最影响判断的一点——**这个字段对不同角色的行为不一样**：

- **你开发自己的项目**：`npm i` 两类全装。
- **别人把你的项目当库安装**（`npm i your-library`）：npm 只装你 `dependencies` 里的包，**你的 devDependencies 一概不装**——因为别人要用你的库来"运行"，而你的构建工具、测试框架是**你自己的事**。

```text
开发者 A 写了库 lib-a
  ├─ dependencies: axios          ← 库运行时真的要用
  └─ devDependencies: jest        ← A 自己跑测试用的

开发者 B 使用 lib-a：npm i lib-a
  └─ B 的 node_modules 里：lib-a + axios ✅   jest ❌（不会装）
```

> [!warning] 推论：发库时账本必须记准
> 如果把运行时需要的包错记成 devDependencies，**别人装了你的库直接报 `Cannot find module`**。发库比发应用更不能记错账。
> 同理，`@types/xxx`：给你的**使用者**提供类型的库（如 `@types/express` 配合你暴露的 API）应放 `dependencies`；只给自己测试/脚本用的放 `devDependencies`。

## 五、怎么判断一个包放哪边

按包的"工种"逐个过：

| 包的工种 | 放哪 | 原因 |
| --- | --- | --- |
| 框架/运行时库（express、vue、react） | ✅ dependencies | 运行时 import |
| HTTP 客户端、工具库（axios、lodash、dayjs） | ✅ dependencies | 运行时 import |
| UI 组件库（element-plus、antd） | ✅ dependencies | 运行时渲染需要 |
| 编译器/转译器（typescript、babel、sass） | ✅ devDependencies | 产物是 JS/CSS，工具本身不进产物 |
| 打包器（vite、webpack、esbuild） | ✅ devDependencies | 只在构建期干活 |
| 代码检查/格式化（eslint、prettier） | ✅ devDependencies | 只在写代码时用 |
| 测试框架（jest、vitest） | ✅ devDependencies | 只在跑测试时用 |
| 类型声明 `@types/*` | ⚠️ 看场景 | 给自己编译用 → dev；你的库把类型暴露给使用者 → dependencies |

> [!question] 边界情况：前端项目把 vite 放 dev，但产物在浏览器跑，算"运行时"吗？
> 算，但运行的是**产物**。"运行时"指的是**产物运行时 import 的包**。前端产物是打包后的 bundle，源码里的 `react` 被打了进去——所以 `react` 是 dependencies；`vite` 只是"造产物的机器"，是 devDependencies。
> ==判断对象是"产物"，不是"应用"。==

## 六、不同场景下 npm 怎么装

```bash
npm i                       # 本地开发：两类全装
npm i --omit=dev            # 生产部署：只装 dependencies（旧写法 --production）
npm ci --omit=dev           # CI/部署：按 lock 精确安装，只装 dependencies
npm i --only=dev            # 只装 devDependencies（如纯 lint/测试环境）
```

三种典型环境的对照：

| 场景 | 装什么 | 原因 |
| --- | --- | --- |
| 开发机 `npm i` | 两类全装 | 要编译、要检查、要测试 |
| 生产服务器 / Docker 镜像 | 只装 dependencies | 运行时用不到 dev；少装 = 镜像更小、攻击面更小、安装更快 |
| CI 流水线 | 分阶段 | 构建/测试阶段全装；部署产物阶段 `--omit=dev` |

> [!tip] Dockerfile 里的经典用法
> ```dockerfile
> COPY package*.json ./
> RUN npm ci --omit=dev        # 生产镜像不装构建工具
> COPY . .
> ```
> 构建期需要 devDependencies 的多阶段构建，在 **builder 阶段全装、最终阶段 `--omit=dev`**，镜像体积能差出几百 MB。

## 七、版本号顺带一提

两个字段里的版本都遵循 **semver**（语义化版本）`主.次.补丁`，配前缀符号控制升级范围：

| 写法 | 含义 |
| --- | --- |
| `^1.2.3` | 锁主版本：可升到 `<2.0.0`（npm 默认） |
| `~1.2.3` | 锁到补丁级：可升到 `<1.3.0` |
| `1.2.3` | 精确固定 |
| `latest` / `*` | 永远最新（危险，不建议） |

精确到每个包实际装了什么，由 `package-lock.json` 锁定——所以**lock 文件要提交进仓库**，团队和 CI 才能装到一模一样的版本。

## 八、常见坑

> [!question] 把 typescript 装进了 dependencies，会有问题吗？
> 功能不报错，但部署机器会白装编译器。挪进 devDependencies 即可。

> [!question] 反过来：把 express 装进了 devDependencies，会怎样？
> **本地能跑、上线报错**——生产环境 `npm i --omit=dev` 时根本不会装它，运行时 `Cannot find module 'express'`。这是最危险的一类记错账。

> [!question] 别人装我的库报 `Cannot find module`？
> 检查库的 `dependencies`——运行时要用的包是不是错记成了 devDependencies（见第四节）。

> [!question] yarn / pnpm 一样吗？
> 一样。字段名相同（`dependencies` / `devDependencies`），`-D` 标志通用（yarn 是 `yarn add -D`，pnpm 是 `pnpm add -D`），pnpm 还有 `--prod` 快捷裁剪。账本规则跨工具通用。

## 九、总结

> [!success] 三句话带走
> 1. **产物运行时 import 得到的 → `dependencies`（`npm i`）；只在编译/检查/测试用的 → `devDependencies`（`npm i -D`）。**
> 2. **装"你的项目"的人只看你的 `dependencies`**——发库时账记错，用户直接装不出来。
> 3. **生产部署记得 `--omit=dev`**——镜像更小、装得更快、更安全。
