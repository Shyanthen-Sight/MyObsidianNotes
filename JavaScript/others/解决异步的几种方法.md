# 解决异步的几种方法

> **一句话总结**：JavaScript 处理异步的所有方案，本质都是**「回调 + 事件循环」的不同包装形式**。演进主线是 **回调 → Promise → Generator → async/await**，每一次演进解决的都不是"能不能异步"，而是**"怎么把异步代码写得像同步一样可读、可组合、可错误处理"**。

> [!abstract] 本文脉络
> 1. 异步到底在解决什么问题
> 2. 方法一：回调函数（最原始）
> 3. 方法二：事件监听 / 发布订阅
> 4. 方法三：Promise（重大转折）
> 5. 方法四：Generator + 执行器（过渡形态）
> 6. 方法五：async / await（当前标准答案）
> 7. 方法六：响应式流 RxJS（另一条路）
> 8. 补充：Worker 把同步变异步
> 9. 六种方案横向对比 + 选型决策
> 10. 面试高频考点

## 一、先搞清楚：异步在解决什么

JS 是**单线程**语言，只有一个调用栈。如果一段代码要等 3 秒（网络请求、读文件、定时器），同步执行就会把整个线程卡死——页面白屏、按钮无响应。

所以 JS 用**事件循环 + 任务队列**把"等待"移出主线程：耗时的活儿交给宿主环境（浏览器 / Node）去做，做完了把回调丢回队列，等调用栈空了再执行。

> [!important] 关键认知
> **异步方案从来不改变"谁在等"，只改变"你怎么写"。** 底层永远是：注册回调 → 事件循环调度 → 触发回调。区别只在于**语法形态**和**错误传播方式**。

由此可以理解各种方案的定位：

| 方案 | 本质 |
|---|---|
| 回调函数 | 异步的原生形态 |
| 事件监听 | 回调的"一对多 + 多次触发"版 |
| Promise | 把回调**对象化**，从而可链式、可组合 |
| Generator | 把"暂停/恢复"能力交给用户代码 |
| async/await | Promise + Generator 的**语法糖** |
| RxJS | 把异步值变成**可组合的数据流** |

## 二、方法一：回调函数（Callback）

最原始也最直接的方案：**把"稍后要执行的代码"作为参数传进去**。

```js
function getData(callback) {
  setTimeout(() => {
    callback("数据到了");
  }, 1000);
}

getData((data) => {
  console.log(data); // 1 秒后：数据到了
});
```

### 约定：错误优先（Error-First）

Node.js 生态确立的规范——回调的**第一个参数永远是错误对象**：

```js
fs.readFile("a.txt", "utf8", (err, data) => {
  if (err) {
    console.error("读取失败", err);
    return; // 必须 return，否则会继续往下执行
  }
  console.log(data);
});
```

### 缺点（正是后面所有方案的动机）

```js
// 三层嵌套：登录 → 取用户信息 → 取订单 → 取订单详情
login(user, (err, token) => {
  if (err) return handle(err);
  getUser(token, (err, user) => {
    if (err) return handle(err);
    getOrders(user.id, (err, orders) => {
      if (err) return handle(err);
      getDetail(orders[0].id, (err, detail) => {
        if (err) return handle(err);
        console.log(detail); // 金字塔，还在往右长
      });
    });
  });
});
```

> [!warning] 回调的四大痛点
> 1. **回调地狱**：横向金字塔，逻辑被嵌套结构切碎（详见 [[回调地狱（Callback hell）]]）
> 2. **错误处理分散**：每个层级都要写 `if (err)`，漏一个就静默失败
> 3. **无法 return / 无法 try-catch**：异步的错误不会被外层 try 捕获
> 4. **无法组合、无法取消**：想做"三个请求并发"得自己写计数器

> [!tip] 回调本身没罪
> 简单场景仍然首选回调：`setTimeout`、`array.forEach`、一次性 DOM 事件。问题只出在**依赖链**上。

## 三、方法二：事件监听 / 发布订阅

回调的升级版：不指定"谁来回调我"，而是"**广播事件，谁关心谁监听**"。

```js
// 浏览器
button.addEventListener("click", onClick);

// Node.js
const EventEmitter = require("events");
const bus = new EventEmitter();

bus.on("order:paid", (order) => sendSms(order));
bus.on("order:paid", (order) => updateStock(order)); // 一对多

bus.emit("order:paid", { id: 1 });
```

### 特点与适用

- ✅ **一对多**：一个事件可以触发多个互不相关的处理逻辑（解耦利器）
- ✅ **多次触发**：适合持续性的信号（点击、消息、数据流）
- ❌ **不知道"何时结束"**：没有终点概念，难以串成流程
- ❌ **难以组合**：做不了"三个事件都完成后执行"
- ❌ **容易泄漏**：忘记 `removeEventListener` / `off` 就会内存泄漏

> [!note] Node 的 Stream 就是事件监听的典型应用
> `stream.on("data")`、`stream.on("end")`、`stream.on("error")` —— 数据分块到达，天然是"多次触发"模型，这正是它不适合用 Promise 表达的原因（Promise 只能 resolve 一次）。

## 四、方法三：Promise（真正的转折点）

Promise 的核心创新不是"新的回调写法"，而是**把"未来的值"变成了一个对象**。对象就能传递、能链式、能组合。

### 4.1 三种状态，单向不可逆

```
pending ──resolve──▶ fulfilled
   └─────reject───▶ rejected
```

一旦敲定，永久固定——这也是"Promise 不能取消、不能重置"的根源。

### 4.2 链式调用：把金字塔拍平

```js
login(user)
  .then((token) => getUser(token))
  .then((user) => getOrders(user.id))
  .then((orders) => getDetail(orders[0].id))
  .then((detail) => console.log(detail))
  .catch((err) => handle(err)); // 一个 catch 兜住全链路
```

> [!tip] 链式之所以能"拍平"，靠的是 `.then` 返回**新 Promise**
> 而**错误能一路冒泡到最近的 `.catch`**，是因为 reject 会沿链向后传递，直到被捕获。这一条就解决了回调方案"每层写 if (err)"的痛点。

### 4.3 两种典型错误写法

```js
// ❌ 断了链：内层 promise 没 return，外层拿不到结果，也捕获不到内层错误
fetchUser().then((user) => {
  fetchOrders(user.id).then((orders) => console.log(orders));
});

// ✅ return 才能续上链
fetchUser().then((user) => {
  return fetchOrders(user.id);
}).then((orders) => console.log(orders));
```

```js
// ❌ Promise 构造反模式：把一个已有 promise 再包一层
new Promise((resolve) => resolve(fetch(url)));

// ✅ 直接返回
return fetch(url);
```

### 4.4 并发原语：Promise 最被低估的能力

单个 Promise 只是"一个未来值"；**组合方法才是 Promise 的真正威力**：

| 方法 | 语义 | 结果形态 | 典型场景 |
|---|---|---|---|
| `Promise.all` | 全部成功才成功，**一个失败立即失败** | 结果数组（按入参顺序） | 并发拉多个互不依赖的数据 |
| `Promise.allSettled` | 等全部结束，**不短路** | `[{status,value\|reason}]` | 批量任务，允许部分失败 |
| `Promise.race` | **第一个敲定**的（成功或失败） | 单个结果 | 超时控制 |
| `Promise.any` | **第一个成功**的（全失败才失败） | 单个结果 | 多镜像源取最快 |
| `Promise.resolve/reject` | 包成 Promise | — | 统一返回值类型 |

```js
// 超时控制的经典写法
const timeout = (p, ms) =>
  Promise.race([
    p,
    new Promise((_, reject) => setTimeout(() => reject(new Error("超时")), ms)),
  ]);
```

详见 [[24-Promise-API]]、[[Promise 链式调用与 Promise.all 流程图解]]。

> [!warning] Promise 的三个遗留短板
> 1. **不能取消**（需要 AbortController 补救，见第六节）
> 2. **只能产出一个值**（不适合数据流）
> 3. **链式太长时仍有"then 汤"**（于是有了 async/await）

## 五、方法四：Generator + 执行器（过渡形态）

这是理解 async/await **为什么能工作**的关键一环，面试也常考。

### 5.1 Generator 的本质：可暂停的函数

```js
function* gen() {
  const a = yield 1;
  console.log("收到", a);
  const b = yield 2;
  return a + b;
}

const it = gen();
it.next();      // { value: 1, done: false }
it.next(10);    // 打印"收到 10"，返回 { value: 2, done: false }
it.next(20);    // { value: 30, done: true }
```

`yield` 能**把执行权交出去**，`next(v)` 能**把值送回来**——这正好是"等待异步结果再继续"所需要的机制。

### 5.2 手写一个 co 执行器（20 行看懂 async/await）

```js
function co(genFn) {
  return new Promise((resolve, reject) => {
    const it = genFn();

    function step(method, arg) {
      let res;
      try {
        res = it[method](arg); // next 或 throw
      } catch (e) {
        return reject(e);
      }
      if (res.done) return resolve(res.value);
      // 把 yield 出来的 promise 接上，完成后自动 next
      Promise.resolve(res.value).then(
        (v) => step("next", v),
        (e) => step("throw", e),
      );
    }

    step("next");
  });
}

// 使用：异步代码写得像同步
co(function* () {
  const token = yield login(user);
  const user2 = yield getUser(token);
  const orders = yield getOrders(user2.id);
  console.log(orders);
}).catch(handle);
```

> [!important] async/await 就是"内置了 co 的 Generator"
> ```js
> // 上面这段，等价于：
> async function run() {
>   const token = await login(user);
>   const user2 = await getUser(token);
>   const orders = await getOrders(user2.id);
> }
> ```
> 语言层面把 `yield + 执行器` 固化成了 `await + async`，于是不需要第三方库（曾经的 `co`、`bluebird` 都因此衰落）。

### 5.3 Generator 在今天还有价值吗

有，但不在"写异步流程"上：

- **异步生成器 + `for await...of`**：处理分页、流式数据
- **无限序列 / 惰性求值**：`function* idMaker() { let i = 0; while (true) yield i++; }`
- **redux-saga** 等库的流程编排

```js
async function* paginate(url) {
  let page = 1;
  while (true) {
    const res = await fetch(`${url}?page=${page++}`);
    const list = await res.json();
    if (!list.length) return;
    yield* list;
  }
}

for await (const item of paginate("/api/orders")) {
  console.log(item); // 拿到一条处理一条，内存友好
}
```

## 六、方法五：async / await（当前标准答案）

### 6.1 本质：Promise 的语法糖

```js
async function f() {
  return 1;
}
// 完全等价于
function f() {
  return Promise.resolve(1);
}
```

- `async` 函数**永远返回 Promise**（返回值会被自动包装）
- `await` **只能在 async 函数内**（或 ESM 顶层，见 6.4）

### 6.2 await 不是"阻塞"，是"挂起"

这是最容易误解的一点：

```js
async function handle() {
  console.log("A");
  const v = await p;   // 函数在此挂起，移出调用栈
  console.log("B");    // p 敲定后，函数被重新压栈，从这里继续
}
```

> [!note] 背后发生的事
> 遇到 `await` → 函数执行被**挂起并移出调用栈**（所以不阻塞主线程，页面不卡）→ Promise 敲定后 → 函数被重新放回调用栈，从断点继续执行。和 [[23-async与await]] 里讲的完全一致。

### 6.3 最大的坑：把并行写成了串行

```js
// ❌ 串行：总耗时 = 3 + 2 = 5 秒
const a = await fetchA(); // 3s
const b = await fetchB(); // 2s

// ✅ 并行：总耗时 = max(3, 2) = 3 秒
const [a, b] = await Promise.all([fetchA(), fetchB()]);
```

> [!important] 一条铁律
> **只要两个 await 之间没有数据依赖，就必须用 `Promise.all` 并行。** "先 await 再 await"是 async/await 最高频的性能事故。

### 6.4 循环里的 await

```js
// 1️⃣ for...of + await：串行，一个一个来（有依赖时用）
for (const id of ids) {
  results.push(await fetchOne(id));
}

// 2️⃣ 先 map 出 Promise 数组，再 all：并行（无依赖时用）
const results = await Promise.all(ids.map((id) => fetchOne(id)));

// 3️⃣ forEach + await：❌ 陷阱，外层不会等
ids.forEach(async (id) => {
  await fetchOne(id); // 这个 await 只作用于回调内部
});
```

### 6.5 错误处理

```js
try {
  const data = await fetchData();
} catch (err) {
  console.error(err);
} finally {
  loading.value = false; // 无论成败都执行
}
```

> [!tip] 不想满屏 try-catch？用"元组式"包装
> ```js
> const [err, data] = await fetchData().then(
>   (d) => [null, d],
>   (e) => [e, null],
> );
> if (err) return handle(err);
> ```
> 这是 Go 风格的错误处理，适合连续多步调用的场景。

### 6.6 顶层 await（ES2022）

```js
// 在 ESM 模块顶层可以直接 await，无需包一层 async 函数
const config = await fetch("/config.json").then((r) => r.json());
export default config;
```
注意：只在 **ES Module** 中可用，CJS 里不行。

### 6.7 取消：async/await 依然不能取消

await 本身没有取消机制，需要 **AbortController**：

```js
const ctrl = new AbortController();

setTimeout(() => ctrl.abort(), 3000); // 3 秒后取消

try {
  const res = await fetch(url, { signal: ctrl.signal });
} catch (err) {
  if (err.name === "AbortError") console.log("已取消");
}
```

> [!warning] 取消是"协作式"的
> `abort()` 只是**通知**，真正响应取消的是 `fetch` 等支持 `signal` 的 API。自己写的 Promise 必须手动检查 `signal.aborted` 才会真的停下。

## 七、方法六：响应式流（RxJS）——另一条路

前面所有方案都在回答"**一个**异步结果怎么拿到"。RxJS 回答的是另一个问题："**一连串**异步事件怎么组合"。

| 维度 | Promise | Observable |
|---|---|---|
| 值的个数 | 1 个 | 0 ~ 无限个 |
| 何时开始 | 创建即执行（eager） | 订阅才执行（lazy） |
| 能否取消 | 不能 | `unsubscribe()` 天然支持 |
| 组合能力 | 有限（all/race） | 数十个操作符（防抖、节流、切换、合并…） |
| 学习成本 | 低 | 高 |

```js
// 搜索框：输入停止 300ms 才请求，且自动取消上一次未完成的请求
fromEvent(input, "input")
  .pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap((e) => ajax(`/search?q=${e.target.value}`)),
  )
  .subscribe((res) => render(res));
```

这几行用原生写法要写不少样板代码。

> [!tip] 什么时候值得引入 RxJS
> - 事件流密集（拖拽、滚动、输入联想、WebSocket 消息）
> - 需要"取消上一次请求"这类切换语义（`switchMap`）
> - **不是**所有项目都需要——普通 CRUD 用 async/await 就够了，硬上 RxJS 反而增加复杂度。

## 八、补充：Worker —— 把"同步"变成异步

严格说这不是"解决异步"，而是解决**异步方案解决不了的问题**：

> [!important] 事件循环只能解决"I/O 等待"，解决不了"CPU 计算"
> 一个 5 秒的 `for` 循环无论怎么包 Promise / async，都仍然占用主线程 5 秒——因为它**没有让出执行权**。

```js
// 主线程
const worker = new Worker("worker.js");
worker.postMessage({ data: bigArray });
worker.onmessage = (e) => console.log("算完了", e.data);

// worker.js
self.onmessage = (e) => {
  const result = heavyCompute(e.data);
  self.postMessage(result);
};
```

Node.js 里对应 `worker_threads`；CPU 密集也可以交给子进程。

> [!note] async 不会让计算变快
> 给同步代码套 `async` 只是多了一层 Promise，计算时间一秒不少。真正的解法是**换线程**或**降低计算量**。

## 九、六种方案横向对比

| 方案 | 可读性 | 错误处理 | 能否取消 | 值的个数 | 组合能力 | 适用场景 |
|---|---|---|---|---|---|---|
| 回调 | ★☆ | 差（逐层判断） | 需手写 | 1 | 差 | 极简场景、一次性回调 |
| 事件监听 | ★★ | 中（各自处理） | `off` 移除 | 多次 | 差 | UI 事件、流、组件通信 |
| Promise | ★★★ | 好（catch 冒泡） | ✗ | 1 | 强（all/race…） | 并发编排、API 封装 |
| Generator | ★★ | 中 | 可中断 | 多次 | 中 | 惰性序列、分页流、saga |
| async/await | ★★★★★ | 好（try-catch） | 需 AbortController | 1 | 强（配合 Promise 静态方法） | **默认选择** |
| RxJS | ★★☆ | 中（catchError） | ✓ 天然支持 | 无限 | ★★★★★ | 复杂事件流 |
| Worker | — | — | `terminate` | — | — | CPU 密集计算 |

## 十、选型决策（照着走）

```
是 CPU 密集计算吗？
├─ 是 → Worker / worker_threads（换线程）
└─ 否 → 是持续的多次事件流吗？
        ├─ 是 → 事件监听（简单）/ RxJS（需要组合、切换、取消）
        └─ 否 → 是一次性的异步结果吗？
                ├─ 是 → 用 async/await
                │        ├─ 多个无依赖 → Promise.all
                │        ├─ 允许部分失败 → Promise.allSettled
                │        ├─ 需要超时 → Promise.race
                │        └─ 需要取消 → AbortController
                └─ 是"可暂停的序列"吗 → Generator / 异步生成器
```

> [!tip] 一句话记法
> **默认 async/await；并发用 Promise.all；事件流用监听/RxJS；算不完用 Worker。**

## 十一、面试高频考点

### 1. 输出顺序题

```js
async function async1() {
  console.log("async1 start");
  await async2();
  console.log("async1 end");
}
async function async2() {
  console.log("async2");
}

console.log("script start");
setTimeout(() => console.log("setTimeout"), 0);
async1();
new Promise((resolve) => {
  console.log("promise1");
  resolve();
}).then(() => console.log("promise2"));
console.log("script end");
```

<details>
<summary>答案</summary>

```
script start
async1 start
async2
promise1
script end
async1 end
promise2
setTimeout
```

要点：`await` 之后的代码进入**微任务队列**；`new Promise` 的执行器是**同步立即执行**；微任务全部清空后才轮到 `setTimeout`（宏任务）。

</details>

### 2. Promise.all 与 allSettled 的区别

一句话：**all 会短路（一个 reject 立刻整体 reject），allSettled 不会（永远等全部结束，返回每个的状态）**。

### 3. 手写题

- `promisify(fn)`：把 err-first 回调函数转成 Promise 版
- `Promise.all`：计数器 + 结果数组按序填充
- `co`：本文第五节已给出

```js
// promisify 参考实现
const promisify = (fn) => (...args) =>
  new Promise((resolve, reject) =>
    fn(...args, (err, data) => (err ? reject(err) : resolve(data))),
  );
```

### 4. 如何取消一个 Promise

原生做不到。三条路：
1. `AbortController` + 支持 signal 的 API（推荐）
2. 包一层 `Promise.race` 让别人赢（"假取消"，底层仍在跑）
3. 自己维护 `isCancelled` 标志位，在关键节点检查（协作式）

## 小结

> [!abstract] 记住这五句
> 1. 所有异步方案的底层都是**回调 + 事件循环**，差别只在语法和错误传播。
> 2. **Promise 的价值不在写法，而在"可组合"**——all / allSettled / race / any。
> 3. **async/await 是 Promise 的语法糖**，本质是内置了 co 执行器的 Generator。
> 4. async/await 最大的坑是**把并行写成了串行**（该用 Promise.all 的地方连着 await）。
> 5. 异步解决不了 CPU 密集——那是 Worker 的活。
