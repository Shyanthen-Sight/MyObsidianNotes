# 事件循环（Event Loop）

> [!info] 视频来源
> **JavaScript Event Loop & Asynchronous Programming** — freeCodeCamp.org · 时长 46:22
> [原视频链接](https://www.youtube.com/watch?v=jzOy07fw2vY)

## 一句话总结

JavaScript 只有**一个调用栈**。它把「等待」这件事外包给 **Web APIs**，再用 **任务队列 / 微任务队列 / 事件循环** 三件套把回调送回栈里执行——于是单线程也能非阻塞。

---

## 1. 浏览器运行时全景（00:00 - 02:13）

事件循环只是整个系统里的一小部分。真正的运行时由五块组成：

![[assets/事件循环-01-浏览器运行时全景.jpg]]
*浏览器 / JS 运行时的五大组件：Call Stack、Web APIs、Task Queue、Microtask Queue、Event Loop*

| 组件 | 职责 |
|---|---|
| **JS 引擎 + 调用栈** | 唯一真正执行代码的地方，后进先出 |
| **Web APIs 环境** | 浏览器提供的"外挂"能力：定时器、网络、DOM、事件、存储… |
| **任务队列（Task / Callback Queue）** | 宏任务回调排队处，先进先出 |
| **微任务队列（Microtask Queue）** | 高优先级队列，Promise 回调等在此排队 |
| **事件循环（Event Loop）** | 调度器：栈空了就把队列里的任务搬进栈 |

> [!tip] 核心认知
> `setTimeout`、`fetch`、`addEventListener`、`console` **都不是 JavaScript 语言本身**，而是浏览器（宿主环境）提供的 Web API。这也是为什么 Node.js 里没有 DOM，却有另一套等价机制。

---

## 2. 调用栈与同步执行（02:13 - 04:33）

```js
console.log("start");

function run() {
  console.log("run");
}

run();
console.log("end");
// 输出：start → run → end
```

执行过程：

1. 代码运行前，先创建**全局执行上下文**压入调用栈
2. 逐行执行；遇到函数调用 → 创建**函数执行上下文**压栈
3. 函数返回 → 上下文弹栈
4. 脚本结束 → 全局上下文弹栈，栈清空

![[assets/事件循环-02-调用栈与执行上下文.jpg]]
*全局执行上下文位于栈底，函数调用依次压栈、执行、弹栈*

> [!note] 特点
> 简单、可预测，天然适合同步代码。但栈是**唯一**的——同一时刻只能做一件事。

---

## 3. 调用栈的局限（04:33 - 06:46）

现实中的代码需要等待：定时器、网络请求、DOM 更新、本地存储、用户交互……

而调用栈**没有暂停/延迟的能力**：一个长任务会占住栈，后续所有代码被堵死，页面直接卡死（白屏、点不动）。

![[assets/事件循环-03-调用栈的局限.jpg]]
*栈被长任务占满 → 后续任务全部阻塞*

> [!warning] 结论
> 栈不能等，所以"等待"必须搬到栈外面去完成——这就是 Web APIs 存在的理由。

## 4. Web APIs：JavaScript 的超能力（06:46 - 10:02）

Web APIs 是**浏览器环境**提供的能力，不是 JS 语言的一部分，通过 `window` 全局对象暴露：

![[assets/事件循环-04-WebAPI超能力.jpg]]
*Web APIs 环境：console、Timers、Fetch、DOM、Events、Storage、Geolocation…*

| Web API | 典型方法 | 用途 |
|---|---|---|
| **Timer** | `setTimeout` / `setInterval` | 延迟、轮询 |
| **Fetch / HTTP** | `fetch` | 网络请求 |
| **DOM** | `getElementById` / `createElement` | 操作界面 |
| **Event** | `addEventListener` | 监听用户交互 |
| **Storage** | `localStorage` / `sessionStorage` | 本地存储 |
| **Geolocation** | `getCurrentPosition` | 获取定位 |
| **Console** | `console.log` | 输出 |

> [!important] 最容易答错的点
> 面试常问"`setTimeout` 是 JS 的内置函数吗？"——**不是**，它由宿主环境（浏览器/Node）提供。

## 5. setTimeout：一次完整的异步流程（10:02 - 14:21）

```js
console.log("start");

setTimeout(() => {
  console.log("Inside setTimeout");
}, 4000);

console.log("end");
// 输出：start → end → Inside setTimeout
```

为什么不是 `start → Inside setTimeout → end`？六步拆解：

1. 全局执行上下文入栈
2. `console.log("start")` → 委托 console API → 打印 **start**
3. `setTimeout` → 委托 **Timer API**，回调 `CBT` 注册进 Web APIs，同时计时器开始倒计时 4 秒；**栈不等，继续往下走**
4. `console.log("end")` → 打印 **end**，全局上下文弹栈，栈清空
5. 4 秒到 → 回调就绪，但它**不能直接进栈**（会打断栈里正在执行的代码），于是进入**任务队列**排队
6. 事件循环发现栈空 → 从队列取出回调压栈执行 → 打印 **Inside setTimeout**

![[assets/事件循环-05-setTimeout执行流程.jpg]]
*setTimeout 全流程：栈 → Timer API → 任务队列 → 事件循环 → 栈*

## 6. 任务队列 / 回调队列（14:21 - 16:34）

回调在 Web APIs 中"就绪"后，统一进入**任务队列（Task Queue，也叫 Callback Queue）**，遵循先进先出。

![[assets/事件循环-06-任务队列.jpg]]
*回调就绪后进入任务队列排队，等待事件循环调度*

---

## 7. 事件循环：连接队列与调用栈（16:34 - 19:00）

事件循环是一个**永不停止的循环**，只做一件事：

```
while (true) {
  if (调用栈为空 && 队列中有任务) {
    取出队首任务 → 压入调用栈执行;
  }
}
```

![[assets/事件循环-07-事件循环桥接.jpg]]
*事件循环在栈与队列之间充当"搬运工"*

> [!important] 铁律
> **事件循环绝不会在调用栈非空时插入任何任务**。它必须等栈彻底清空，才会搬运下一个任务——这正是 JS 单线程语义不被破坏的根本原因。

---

## 8. 例：Geolocation 与用户授权（19:00 - 22:26）

```js
navigator.geolocation.getCurrentPosition(
  (position) => console.log(position),  // 成功回调
  (error) => console.log(error)         // 失败回调
);
```

- `getCurrentPosition` 属于 Web API → 立即交给浏览器，栈继续执行
- 浏览器弹出授权框，用户点"允许"或"拒绝"（**耗时完全不可控**）
- 回调就绪 → 进任务队列 → 事件循环调度 → 执行
- 与我们之前看到的 setTimeout 流程**完全一致**

---

## 9. 例：DOM 事件与监听器（22:26 - 27:23）

```js
console.log("start");

const button = document.getElementById("btn");
button.addEventListener("click", () => {
  console.log("Button clicked");
});

console.log("end");
// 输出：start → end →（点击时）Button clicked
```

![[assets/事件循环-08-DOM事件监听.jpg]]
*事件回调只是被注册，直到用户点击才进入任务队列*

> [!tip] 三个例子其实是同一套流程
> setTimeout / Geolocation / DOM 事件：**都是在 Web API 注册回调 → 就绪后进任务队列 → 事件循环在栈空时搬运执行**。掌握一个，就掌握全部。

## 10. Promise、Fetch 与微任务队列（27:23 - 34:54）

```js
console.log("start");

setTimeout(() => {
  console.log("Inside setTimeout");
}, 4000);

fetch("https://www.abc.com/data")
  .then(() => {
    console.log("Data received");
  });

console.log("end");
```

关键差异：**Promise 的回调不进任务队列，而是进微任务队列（Microtask Queue）**。

![[assets/事件循环-09-Promise与微任务队列.jpg]]
*CBP（promise 回调）进入 Microtask Queue，CBT（定时器回调）进入 Task Queue*

| 对比项  | 任务队列（宏任务）                                 | 微任务队列                                                                  |
| ---- | ----------------------------------------- | ---------------------------------------------------------------------- |
| 典型来源 | setTimeout、setInterval、Geolocation、DOM 事件 | Promise.then/catch/finally、async/await、MutationObserver、queueMicrotask |
| 优先级  | 低                                         | **高**                                                                  |
| 调度时机 | 栈空且微任务队列已空                                | 栈一空就立刻全部执行完                                                            |

> [!important] 执行顺序规则
> 1. 先执行完所有**同步代码**
> 2. 清空**微任务队列**（且清空过程中新产生的微任务也一并执行）
> 3. 再取**一个**宏任务执行，执行完回到第 2 步

---

## 11. 长任务下的执行顺序（34:54 - 38:35）

如果第 11 行开始是一段**超长同步代码**（比如百万行循环）：

1. 栈被长任务占满，定时器 4 秒到了、fetch 也返回了
2. 两个回调分别在**任务队列**和**微任务队列**里干等
3. 长任务结束、全局上下文弹栈 → 栈空
4. 事件循环**先清空微任务队列**（Data received），再取宏任务（Inside setTimeout）
5. 最终输出：`start → end → Data received → Inside setTimeout`

![[assets/事件循环-10-长任务与执行顺序.jpg]]
*长任务占栈期间，两个队列都在排队；栈空后微任务优先*

---

## 12. 微任务队列里到底有什么（38:35 - 41:05）

只有四类东西会进微任务队列：

![[assets/事件循环-11-微任务队列的内容.jpg]]
*微任务队列的四个来源*

1. **Promise 回调**：`.then` / `.catch` / `.finally`，包括 Promise 链式调用
2. **MutationObserver**：监听 DOM 变化的回调
3. **async/await**：`await` 关键字之后的代码（本质是 Promise 的语法糖）
4. **queueMicrotask()**：手动把函数塞进微任务队列

其余所有异步回调——定时器、定位、事件、网络（回调部分）——一律进**任务队列**。

> [!tip] 输出顺序题怎么秒答
> 先看同步输出 → 再找微任务（Promise/await/queueMicrotask）→ 最后按注册顺序排宏任务。这个顺序背下来，90% 的题都能秒。

---

## 13. 微任务饥饿（41:05 - 44:59）

如果微任务在执行过程中**不断产生新的微任务**：

```js
function loop() {
  Promise.resolve().then(loop); // 永不停止地产生新微任务
}
loop();
// 任务队列里的回调将永远得不到执行
```

事件循环每隔一轮都会优先检查微任务队列。只要微任务队列不空，宏任务就永远排队——这就是**微任务饥饿（Starvation）**。

![[assets/事件循环-12-微任务饥饿.jpg]]
*微任务不断自我复制 → 任务队列被"饿死"*

> [!warning] 实际影响
> 死循环式的微任务会让页面完全无响应（比长任务更彻底），因为连渲染和用户事件回调都进不来。

## 14. 总结与面试速查（44:59 - 46:22）

### 记忆口诀

> **栈执行、API 托管、队列排队、循环搬运、微任务插队。**

### 经典输出题

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");
// 输出：1 → 4 → 3 → 2
```

原因：同步先跑完（1、4），然后清空微任务（3），最后取宏任务（2）。

### 高频问答

| 问题 | 答案要点 |
|---|---|
| JS 是单线程吗？ | 是，只有一个调用栈；异步靠宿主环境的 Web APIs |
| 事件循环的作用？ | 栈空时把队列中的任务搬进栈，是栈与队列之间的桥 |
| 宏任务 vs 微任务？ | 微任务优先级更高；每轮宏任务后必须清空微任务队列 |
| setTimeout(fn, 0) 是立即执行吗？ | 不是，最少要等栈清空 + 一轮事件循环 |
| 为什么 Promise 比 setTimeout 先执行？ | Promise 回调进微任务队列，优先级高于任务队列 |
| 什么是微任务饥饿？ | 微任务不断产生新微任务，导致宏任务永远排队 |
| 长任务为什么卡页面？ | 占满唯一的调用栈，渲染与事件回调都无法进入 |
