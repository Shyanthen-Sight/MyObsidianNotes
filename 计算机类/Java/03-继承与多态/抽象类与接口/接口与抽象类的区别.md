# Java 接口与抽象类的区别

> 接口与抽象类都能声明“子类型必须遵守的契约”，因此常被放在一起比较。
> 真正的区别不在语法，而在设计意图：==抽象类描述“是什么”，并可以携带共享状态与实现；接口描述“能做什么”，只承诺行为==。

## 1. 同一个问题，两种抽象

继续使用薪资系统。下面两段代码都能约束“必须能算工资”：

```java
abstract class Employee {
    protected String name;
    protected double baseSalary;

    public abstract double calculateSalary();
}
```

```java
interface Payable {
    double calculateSalary();
}
```

如果只看方法签名，它们几乎一样。但约束范围完全不同：

| 设计 | 谁可以使用 | 还能携带什么 |
| --- | --- | --- |
| `abstract class Employee` | 必须是 `Employee` 的子类 | 字段、构造方法、普通方法、模板方法 |
| `interface Payable` | 任何类，只要实现它 | 只能有常量、抽象方法、`default` / `static` / `private` 方法 |

薪资系统里，两个抽象可以同时存在：

```java
abstract class Employee implements Payable {
    protected final String name;
    protected final double baseSalary;

    protected Employee(String name, double baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public String getName() {
        return name;
    }

    public abstract double calculateSalary();
}

interface Payable {
    double calculateSalary();
}
```

`Employee` 负责“员工是什么、共享哪些状态”，`Payable` 负责“能算工资”这一项能力。外部合作方不必继承 `Employee`，只要实现 `Payable`，也能接入工资结算。

## 2. 语法对比

| 维度 | 抽象类 | 接口 |
| --- | --- | --- |
| 声明关键字 | `abstract class` | `interface` |
| 继承 / 实现数量 | 类只能==单继承==一个抽象类 | 类可以==实现多个==接口；接口可以多继承接口 |
| 构造方法 | ✅ 有，供子类 `super(...)` 调用 | ❌ 没有 |
| 实例字段 | ✅ 可以有，保存每个对象的状态 | ❌ 不能有；字段隐式 `public static final` 常量 |
| 方法类型 | 抽象方法、普通方法、`static`、`final` | 抽象方法、`default`、`static`、`private` |
| 访问修饰符 | 四个都可以用（类、字段、方法） | 方法隐式 `public`（Java 9+ 可有 `private`）；字段隐式 `public` |
| 能否实例化 | ❌ | ❌ |
| 多态方式 | 父类引用指向子类对象 | 接口引用指向实现类对象 |
| 设计语义 | ==is-a==：是一种 | ==can-do==：能做到 |
| 版本演进 | 新增抽象方法会破坏所有具体子类 | 新增 `default` 方法可以不破坏实现类 |

> [!note] “接口完全不能有方法体”已经过时
> Java 8 起接口可以有 `default`、`static` 方法，Java 9 起可以有 `private` 方法。但接口==仍然不能有实例字段和构造方法==，这是它与抽象类最硬的分界线。

## 3. 设计语义对比

### 3.1 抽象类：是什么 + 共享实现

抽象类表达的是一种==“是一种”==的关系：

```java
abstract class Employee {
    protected final String name;

    protected Employee(String name) {
        this.name = name;
    }

    public abstract double calculateSalary();

    public final void printPayslip() {          // 共享流程
        System.out.println("姓名：" + name);
        System.out.println("应发：" + calculateSalary());
    }
}

class Manager extends Employee {
    Manager(String name) {
        super(name);
    }

    @Override
    public double calculateSalary() {
        return 7000;
    }
}
```

`Manager` ==是一个== `Employee`，它继承字段 `name`、构造方法要求和 `printPayslip()` 流程，只需要补上自己的工资算法。

适合抽象类的信号：

1. 子类需要共享==实例字段==；
2. 子类需要共享==部分方法实现==；
3. 需要构造方法保证对象创建时的不变量；
4. 需要模板方法固定流程；
5. 类型之间确实是“是一种”的关系，并且只应有一个父类。

### 3.2 接口：能做什么

接口表达的是一种==“能做到”==的能力：

```java
interface Payable {
    double calculateSalary();
}

interface Workable {
    void work();
}

class Manager implements Payable, Workable {
    @Override
    public double calculateSalary() {
        return 7000;
    }

    @Override
    public void work() {
        System.out.println("经理在开会");
    }
}
```

`Manager` ==能==算工资，也==能==工作。这两个能力可以分给完全不同的类型：经理、小时工、外部合作方、甚至一个 `Robot`。接口不要求它们共享同一个父类。

适合接口的信号：

1. 只关心==行为契约==，不需要共享状态；
2. 一个类需要同时具备==多种能力==；
3. 需要跨继承体系解耦，让不相关的类协作；
4. 需要回调、策略、插件式的扩展点；
5. 作为对外 API 的边界，只暴露必要的方法。

### 3.3 一句话概括

> ==抽象类是对一组类的抽象，接口是对一组行为的抽象。==
> 抽象类回答“你是谁”，接口回答“你能做什么”。

## 4. 什么时候用抽象类

### 4.1 共享状态与通用实现

```java
abstract class Employee {
    protected final String name;
    protected final double baseSalary;

    protected Employee(String name, double baseSalary) {
        if (name == null || name.trim().isEmpty()) {
            throw new IllegalArgumentException("姓名不能为空");
        }
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public String getName() {
        return name;
    }

    public double getBaseSalary() {
        return baseSalary;
    }

    public abstract double calculateSalary();
}
```

`name`、`baseSalary` 以及姓名校验逻辑只写一次，所有子类直接复用。接口做不到这一点：它不能保存实例字段，也不能在接口里写构造方法。

### 4.2 模板方法

```java
abstract class Employee {
    // ...

    public final void printPayslip() {
        System.out.println("===== 工资单 =====");
        System.out.println("姓名：" + getName());
        System.out.println("应发：" + calculateSalary());
        System.out.println("==================");
    }

    public abstract double calculateSalary();
}
```

流程由父类固定，变化点交给子类。`final` 保证子类不能破坏流程，这是抽象类的典型优势。

### 4.3 需要构造方法保证不变量

```java
abstract class Account {
    protected final String id;
    protected double balance;

    protected Account(String id, double balance) {
        if (id == null || id.isEmpty()) {
            throw new IllegalArgumentException("账户号不能为空");
        }
        if (balance < 0) {
            throw new IllegalArgumentException("余额不能为负数");
        }
        this.id = id;
        this.balance = balance;
    }

    public abstract void withdraw(double amount);
}
```

接口没有构造方法，无法在对象创建时统一做这类校验。

### 4.4 需要单继承表达“是一种”

```java
abstract class Shape {
    public abstract double area();
}

class Circle extends Shape { /* ... */ }
class Rectangle extends Shape { /* ... */ }
```

一个图形就是一种形状，用抽象类表达类型层级很自然。

## 5. 什么时候用接口

### 5.1 只约定能力，不需要共享状态

```java
interface Payable {
    double calculateSalary();
}

interface Workable {
    void work();
}
```

```java
class Manager implements Payable, Workable { /* ... */ }
class HourlyEmployee implements Payable, Workable { /* ... */ }
class ExternalContractor implements Payable { /* ... */ }
```

`ExternalContractor` 不必继承 `Employee`，只要实现 `Payable`，就能被工资结算逻辑处理。

### 5.2 需要多实现

Java 的类只能单继承，但可以实现多个接口：

```java
class Manager extends Employee implements Payable, Workable, Reportable {
    // ...
}
```

抽象类无法同时继承 `Employee`、`Payable`、`Workable` 三个父类；接口可以。

### 5.3 跨继承体系解耦

```java
public static void payAll(Payable[] payables) {
    for (Payable p : payables) {
        System.out.println("应发：" + p.calculateSalary());
    }
}
```

`payAll` 只依赖 `Payable`，不依赖 `Employee`。调用方与实现方之间只共享“能算工资”这一条契约，新增类型时不需要修改 `payAll`。这就是[[面向抽象编程]]。

### 5.4 回调、策略与插件

```java
interface PaymentStrategy {
    void pay(double amount);
}

class AlipayStrategy implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        System.out.println("支付宝支付：" + amount);
    }
}

class WechatStrategy implements PaymentStrategy {
    @Override
    public void pay(double amount) {
        System.out.println("微信支付：" + amount);
    }
}

class Order {
    private PaymentStrategy strategy;

    public Order(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void checkout(double amount) {
        strategy.pay(amount);          // 只依赖接口
    }
}
```

订单不需要知道具体是支付宝还是微信，只依赖 `PaymentStrategy`。运行期可以随时替换实现，这就是==策略模式==。

### 5.5 函数式接口

只有一个抽象方法的接口可以用 Lambda 简化：

```java
@FunctionalInterface
interface Discount {
    double apply(double price);
}

Discount half = price -> price * 0.5;
System.out.println(half.apply(200));    // 100.0
```

抽象类做不到这一点：它可能有多个抽象方法、字段和构造方法，无法用 Lambda 直接实现。

## 6. 组合使用：接口定契约，抽象类做骨架

两者不是二选一。常见做法是==接口定义契约，抽象类提供骨架实现，具体类填细节==：

```java
interface Payable {
    double calculateSalary();
}

abstract class AbstractEmployee implements Payable {
    protected final String name;
    protected final double baseSalary;

    protected AbstractEmployee(String name, double baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public String getName() {
        return name;
    }

    @Override
    public abstract double calculateSalary();   // 仍留给具体子类
}

class Manager extends AbstractEmployee {
    private final double bonus;

    public Manager(String name, double baseSalary, double bonus) {
        super(name, baseSalary);
        this.bonus = bonus;
    }

    @Override
    public double calculateSalary() {
        return baseSalary + bonus;
    }
}
```

结构分三层：

| 层 | 角色 | 例子 |
| --- | --- | --- |
| 接口 | 对外契约 | `Payable`：能算工资 |
| 抽象类 | 骨架实现 | `AbstractEmployee`：共享姓名、基本工资、构造校验 |
| 具体类 | 填变化点 | `Manager`：奖金算法 |

JDK 里大量使用这种结构：

* `List`（接口）→ `AbstractList`（骨架）→ `ArrayList`（具体实现）；
* `Map`（接口）→ `AbstractMap`（骨架）→ `HashMap`（具体实现）；
* `Collection`（接口）→ `AbstractCollection`（骨架）→ 各种集合。

> [!tip] 抽象类实现接口时可以不实现方法
> `AbstractEmployee implements Payable` 并没有实现 `calculateSalary()`，而是继续把它声明为抽象方法。这是合法的：抽象类可以把接口契约继续往下传。

## 7. 常见误区

1. **以为接口已经完全取代抽象类**：接口不能保存实例状态、没有构造方法，也无法提供模板方法所需的字段与流程。两者解决的是不同问题。
2. **以为抽象类只能单继承，所以一定不如接口**：单继承是限制，也是“唯一父类型”的语义保证；接口的多实现适合组合能力，二者互补。
3. **以为接口不能有方法体**：Java 8 起 `default` / `static` 方法可以有方法体，Java 9 起还有 `private` 方法。
4. **以为接口可以有实例字段**：接口字段隐式 `public static final`，本质是常量，不能保存每个对象的状态。
5. **以为 `default` 方法让接口拥有了状态**：默认方法只是行为，接口仍然没有实例字段和构造方法。
6. **以为一个类只能在抽象类和接口中二选一**：可以同时 `extends` 一个抽象类并 `implements` 多个接口。
7. **以为抽象类不能实现接口**：抽象类可以实现接口，并选择只实现一部分方法。
8. **以为接口可以继承抽象类**：接口只能继承接口，不能 `extends` 类。
9. **以为抽象类里必须全是抽象方法**：抽象类可以有普通方法、字段、构造方法，甚至没有抽象方法。
10. **以为“有默认实现就该用抽象类”**：如果没有实例状态，接口的 `default` 方法同样能提供默认实现，而且不占用宝贵的单继承名额。

## 8. 选择清单

按顺序问自己：

1. **需要保存每个对象的实例状态吗？** → 需要：抽象类（接口不能有实例字段）。
2. **需要在创建对象时做统一校验吗？** → 需要：抽象类（接口没有构造方法）。
3. **需要固定一套流程、只留变化点吗？** → 需要：抽象类（模板方法）。
4. **只是约定一组能力，且可能被不相关的类实现吗？** → 接口。
5. **一个类需要同时具备多种能力吗？** → 接口（多实现）。
6. **需要跨继承体系解耦、做回调或策略替换吗？** → 接口。
7. **既要共享实现，又要对外只暴露契约吗？** → 接口 + 抽象骨架（如 `List` / `AbstractList`）。

| 需求 | 首选 |
| --- | --- |
| 共享字段、构造校验、模板方法 | 抽象类 |
| 纯行为契约、多实现、跨体系解耦 | 接口 |
| 既要契约又要骨架 | 接口 + 抽象类 |
| 单个抽象方法、需要 Lambda | 函数式接口 |
| 只是给类打标记 | 标记接口（或注解） |

> [!warning] 不要为了“看起来更面向对象”而过度抽象
> 如果一组类型没有共享状态、也不会新增实现，直接写具体类往往更清楚。抽象类与接口的价值在于隔离==会变化的部分==，而不是让继承层级看起来更漂亮。

## 9. 小结

* 抽象类 = ==is-a + 共享状态 + 共享实现 + 单继承==；
* 接口 = ==can-do + 纯行为契约 + 多实现==；
* 抽象类可以有字段、构造方法、普通方法、模板方法；接口不能有实例字段和构造方法；
* Java 8/9 之后接口有了 `default`、`static`、`private` 方法，但==仍然不携带实例状态==；
* 选择标准是“是否需要共享状态与实现”，而不是“哪个语法更强”；
* 两者可以组合：==接口定契约，抽象类做骨架，具体类填细节==。
