# 存储函数 —— 在 SQL 表达式里调用的自定义函数

> [!abstract] 一句话
> 存储函数是**用 `CREATE FUNCTION` 定义、必须 `RETURNS` 一个类型、用 `RETURN` 返回单个值、能直接写进 `SELECT` / `WHERE` / `ORDER BY` 的数据库程序**。和存储过程的分界线不是"谁更高级"，而是**能不能出现在表达式里**。真正容易翻车的是三件事：**特征声明写错（1418）**、**把函数套在索引列上（索引失效）**、**在函数里做它不允许做的事（事务、结果集、动态 SQL、递归）**。

---

> [!example] 本篇示例数据
> 继续使用 [[条件函数]] 里的 `emp` 表。

```sql
DROP TABLE IF EXISTS emp;
CREATE TABLE emp (
    id        INT AUTO_INCREMENT PRIMARY KEY,
    name      VARCHAR(20) NOT NULL,
    dept      VARCHAR(20),
    gender    CHAR(1),
    salary    DECIMAL(10,2),
    hire_date DATE,
    bonus     DECIMAL(10,2)
);

INSERT INTO emp (name, dept, gender, salary, hire_date, bonus) VALUES
('张伟', '研发部', 'M', 12000.00, '2018-03-11', 5000.00),
('李娜', '研发部', 'F',  9000.00, '2020-07-01',    NULL),
('王强', '研发部', 'M', 15000.00, '2019-05-20', 8000.00),
('赵敏', '销售部', 'F',  8000.00, '2021-09-15', 3000.00),
('陈晨', '销售部', 'M',  6500.00, '2022-02-08',    NULL),

```

## 一、存储函数是什么

一个存储函数必须满足三个硬性条件：

1. 用 `RETURNS type` 声明**返回类型**。
2. 函数体里至少执行到一次 `RETURN value`。
3. 每次调用只返回**一个标量值**（数字、字符串、日期等），不能是一张表。

因此它可以出现在任何"表达式能出现的位置"：

```sql
SELECT fn_salary_level(salary) FROM emp;                 -- SELECT 列表
SELECT * FROM emp WHERE fn_salary_level(salary) = '高';   -- WHERE
SELECT dept, fn_dept_avg(dept) FROM emp GROUP BY dept;    -- GROUP BY
SELECT * FROM emp ORDER BY fn_annual_salary(salary);      -- ORDER BY
```

### 1.1 和存储过程的分界线

| 对比项 | 存储过程 | 存储函数 |
| --- | --- | --- |
| 关键字 | `CREATE PROCEDURE` | `CREATE FUNCTION` |
| 返回值 | 零个或多个（`OUT` / `INOUT` / 结果集） | **有且仅有一个标量值** |
| 调用方式 | `CALL p(...)` | 直接写在表达式里 `f(...)` |
| 参数模式 | `IN` / `OUT` / `INOUT` | **只有输入参数** |
| 能否出现在 `SELECT` / `WHERE` | 不能 | 能 |
| 返回结果集 | 可以 | 不可以 |
| 事务控制 | 可以 `COMMIT` / `ROLLBACK` | 不可以 |
| 动态 SQL | 可以 `PREPARE` / `EXECUTE` | 不可以 |
| 递归 | 可配置 `max_sp_recursion_depth` | 不允许 |
| 典型用途 | 多步写入、批量维护、事务流程 | 单值计算、行级转换、统一口径 |

> [!tip] 选型口诀
> **要"算一个值"用函数，要"做一件事"用过程。**
> 如果逻辑里出现"多行结果""提交/回滚""写多张表"，基本就该用存储过程或应用层，而不是函数。

### 1.2 什么时候值得用函数

- 同一个计算口径被很多 SQL 重复使用：薪资档位、订单金额、手机号脱敏、年龄计算。
- 需要把复杂表达式**命名化**，让 `SELECT` 可读。
- 想把某段只读逻辑收敛到数据库里，并且希望它能参与 `WHERE` / `ORDER BY`。

### 1.3 什么时候不要用

- 需要返回多行多列：用视图或存储过程。
- 需要事务：用存储过程。
- 需要动态拼 SQL：用存储过程。
- 大表上逐行调用：函数会对每一行执行一次，通常比等价的集合 SQL 慢得多。
- 频繁变更的业务规则：改函数要 `DROP` + `CREATE`，版本管理和测试都更麻烦。

## 二、第一个存储函数

### 2.1 最小结构

```sql
DELIMITER //

CREATE FUNCTION fn_annual_salary(p_salary DECIMAL(10,2))
RETURNS DECIMAL(12,2)
DETERMINISTIC
NO SQL
RETURN p_salary * 12 //

DELIMITER ;

SELECT fn_annual_salary(10000);       -- 120000.00
SELECT name, fn_annual_salary(salary) AS 年薪 FROM emp;
```

> [!note] `RETURNS` 和 `RETURN` 不是一回事
> `RETURNS DECIMAL(12,2)` 是**声明返回类型**，只出现一次；
> `RETURN p_salary * 12` 是**真正返回一个值**，可以出现多次。
> 只写 `RETURN` 不写 `RETURNS`，`CREATE FUNCTION` 直接语法错误。

### 2.2 带 `BEGIN...END` 的函数体

```sql
DELIMITER //

CREATE FUNCTION fn_salary_level(p_salary DECIMAL(10,2))
RETURNS VARCHAR(10)
DETERMINISTIC
NO SQL
BEGIN
    IF p_salary IS NULL THEN
        RETURN NULL;
    ELSEIF p_salary >= 12000 THEN
        RETURN '高';
    ELSEIF p_salary >= 8000 THEN
        RETURN '中';
    ELSE
        RETURN '低';
    END IF;
END //

DELIMITER ;

SELECT name, salary, fn_salary_level(salary) AS 档位
FROM emp
ORDER BY salary DESC;
```

```
+--------+----------+--------+
| name   | salary   | 档位   |
+--------+----------+--------+
| 王强   | 15000.00 | 高     |
| 张伟   | 12000.00 | 高     |
| 周杰   |  9500.00 | 中     |
| 李娜   |  9000.00 | 中     |
| 赵敏   |  8000.00 | 中     |
| 刘洋   |  7500.00 | 低     |
| 孙悦   |  7000.00 | 低     |
| 陈晨   |  6500.00 | 低     |
+--------+----------+--------+
```

### 2.3 读表的函数

```sql
DELIMITER //

CREATE FUNCTION fn_dept_avg(p_dept VARCHAR(20))
RETURNS DECIMAL(10,2)
READS SQL DATA
BEGIN
    DECLARE v_avg DECIMAL(10,2);

    SELECT AVG(salary)
      INTO v_avg
      FROM emp
     WHERE dept = p_dept;

    RETURN v_avg;
END //

DELIMITER ;

SELECT fn_dept_avg('研发部');      -- 12000.00
```

这个函数读取表，所以声明 `READS SQL DATA`；它**不能**声明 `NO SQL`，也**不应该**声明 `DETERMINISTIC`——表数据一变，同样参数的结果就会变。

### 2.4 再两个常用例子

```sql
-- 手机号脱敏
DELIMITER //
CREATE FUNCTION fn_mask_phone(p_phone CHAR(11))
RETURNS CHAR(11)
DETERMINISTIC
NO SQL
RETURN CONCAT(LEFT(p_phone, 3), '****', RIGHT(p_phone, 4)) //
DELIMITER ;

SELECT fn_mask_phone('13812345678');   -- 138****5678
```

```sql
-- 1 + 2 + ... + n
DELIMITER //
CREATE FUNCTION fn_sum_to(p_n INT)
RETURNS BIGINT
DETERMINISTIC
NO SQL
BEGIN
    DECLARE i INT DEFAULT 1;
    DECLARE v_sum BIGINT DEFAULT 0;

    WHILE i <= p_n DO
        SET v_sum = v_sum + i;
        SET i = i + 1;
    END WHILE;

    RETURN v_sum;
END //
DELIMITER ;

SELECT fn_sum_to(100);    -- 5050
```

> [!warning] 返回值类型要留足空间
> `DECIMAL(12,2)` 最大约 99 亿，`BIGINT` 上限约 922 亿亿。
> 返回类型装不下时，非严格模式会**截断/警告**，严格模式可能直接报错。金额、计数、累计值宁可放大一档。

## 三、特征声明：`DETERMINISTIC` 与 `NO SQL`

创建函数时，`RETURNS type` 后面可以跟一串特征。它们**不影响函数怎么算**，但直接影响**权限、复制安全和优化器判断**。

| 特征 | 含义 | 典型用法 |
| --- | --- | --- |
| `DETERMINISTIC` | 相同参数总是返回相同结果，且不依赖表数据和会话状态 | 纯计算函数 |
| `NOT DETERMINISTIC` | 默认值；结果可能随数据或环境变化 | 读表、`NOW()`、`RAND()` |
| `NO SQL` | 函数体不执行任何 SQL | 纯计算 |
| `READS SQL DATA` | 函数体只读 SQL | 查询表算值 |
| `MODIFIES SQL DATA` | 函数体会修改数据 | 不推荐 |
| `CONTAINS SQL` | 默认值；表示含 SQL，但未细分类 | 尽量写明确 |
| `SQL SECURITY DEFINER` / `INVOKER` | 以定义者 / 调用者身份执行 | 默认 `DEFINER` |
| `COMMENT '...'` | 备注 | 运维排查 |

### 3.1 默认值是什么

不写特征时，MySQL 按下面的默认值处理：

- `NOT DETERMINISTIC`
- `CONTAINS SQL`
- `SQL SECURITY DEFINER`

> [!danger] 开了二进制日志，创建函数可能直接报 1418
> 只要 `log_bin=ON`，创建函数时通常至少要声明 `DETERMINISTIC`、`NO SQL`、`READS SQL DATA` 三者之一，否则会遇到：
> `ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled`
>
> 先检查环境：
>
> ```sql
> SELECT @@log_bin, @@log_bin_trust_function_creators;
> ```
>
> 网上常见的"一键解决"是：
>
> ```sql
> SET GLOBAL log_bin_trust_function_creators = 1;
> ```
>
> 它确实能让创建通过，但**只是关掉了检查，并没有让函数变安全**。正确做法是先把特征声明写对；只有在完全信任所有能建函数的账号、并且清楚复制风险时，才考虑这个开关。

### 3.2 `DETERMINISTIC` 是承诺，不是缓存

很多人以为声明 `DETERMINISTIC` 之后 MySQL 会缓存结果，不是的：

- 它只是告诉服务器"你可以相信相同输入得到相同输出"。
- **同一个函数在一条 SQL 里被调用 1000 次，函数体就会执行 1000 次**。
- 如果函数实际上读了表、用了 `NOW()` / `RAND()` / `UUID()`，却硬标 `DETERMINISTIC`，在语句级复制下可能导致主从数据不一致。

> [!failure] 乱标 `DETERMINISTIC` 是最隐蔽的坑
> 本地单机测试一切正常，上了主从以后从库结果不同，排查成本极高。
> 判断标准很简单：**函数结果只由参数决定 → `DETERMINISTIC`；碰了表或环境 → 老实用 `READS SQL DATA` / `NOT DETERMINISTIC`。**

### 3.3 不安全函数与复制

- 非确定性函数、修改数据的函数，在语句级复制（`binlog_format=STATEMENT`）下可能被判定为 unsafe。
- 即使使用行级复制，函数内部的写操作也会带来"同一条语句隐式改多行"的审计难题。
- 结论：**函数尽量只读**；写操作交给存储过程或应用层。

## 四、参数与变量

### 4.1 函数参数只有"输入"

```sql
CREATE FUNCTION fn_add(p_a INT, p_b INT)
RETURNS INT
DETERMINISTIC
NO SQL
RETURN p_a + p_b;
```

和存储过程不同：

| 项目 | 存储函数 |
| --- | --- |
| `IN` / `OUT` / `INOUT` | **都不能写**，所有参数天然是输入 |
| 默认参数 | 不支持 |
| 参数重载 | 不支持 |
| 可变参数 | 不支持 |

调用时可以传表达式：

```sql
SELECT fn_annual_salary(salary * 1.1) FROM emp;
SELECT fn_add(1, 2), fn_add(1 + 2, 3 * 4);
```

### 4.2 局部变量与 `SELECT ... INTO`

```sql
DELIMITER //
CREATE FUNCTION fn_dept_max(p_dept VARCHAR(20))
RETURNS DECIMAL(10,2)
READS SQL DATA
BEGIN
    DECLARE v_max DECIMAL(10,2) DEFAULT NULL;

    SELECT MAX(salary)
      INTO v_max
      FROM emp
     WHERE dept = p_dept;

    RETURN v_max;
END //
DELIMITER ;
```

规则和存储过程一致：

- `DECLARE` 必须写在 `BEGIN...END` 的**最前面**，顺序是变量/条件 → 游标 → 处理器。
- 没有 `DEFAULT` 时初值是 `NULL`。
- `SELECT ... INTO` 返回 0 行：不报错，变量保持原值并附 `warning 1329 No data`；返回多行：`ERROR 1172`。

### 4.3 参数名不要和列名同名

```sql
-- 错误示范：dept = dept 恒真
CREATE FUNCTION fn_bad(p_dept VARCHAR(20))
RETURNS INT
READS SQL DATA
BEGIN
    DECLARE v_cnt INT;
    SELECT COUNT(*) INTO v_cnt FROM emp WHERE dept = dept;
    RETURN v_cnt;
END;
```

MySQL 在名称冲突时优先解析列名，过滤条件等于没写。统一用 `p_` / `v_` 前缀。

### 4.4 用户变量 `@x` 能用，但别用

函数里可以读写 `@x`，但它是**会话级状态**，会造成隐藏的副作用：

- 调用顺序不同，结果可能不同。
- 函数看起来"只依赖参数"，实际却依赖会话，违反了 `DETERMINISTIC` 的语义。
- 排障时很难发现是谁改了 `@x`。

函数内部一律用 `DECLARE` 局部变量。

## 五、控制流与返回

存储函数里的 `IF` / `CASE` / `LOOP` / `WHILE` / `REPEAT` / `LEAVE` / `ITERATE` 和存储过程完全一样，区别只在**出口是 `RETURN`**。

### 5.1 `IF` 与 `CASE`

```sql
IF p_salary IS NULL THEN
    RETURN NULL;
ELSEIF p_salary >= 12000 THEN
    RETURN '高';
ELSE
    RETURN '低';
END IF;
```

```sql
CASE
    WHEN p_amount >= 1000 THEN RETURN p_amount * 0.05;
    WHEN p_amount >= 500  THEN RETURN p_amount * 0.03;
    ELSE RETURN 0;
END CASE;
```

> [!danger] 存储程序的 `CASE` 没匹配且没 `ELSE` 会报错
> `ERROR 1339: Case not found for CASE statement`。
> 这跟 `CASE` **表达式**不匹配返回 `NULL` 的行为不同。

### 5.2 每条路径都必须能 `RETURN`

```sql
-- 错误示范：p_n <= 0 时没有 RETURN
CREATE FUNCTION fn_bad(p_n INT)
RETURNS INT
DETERMINISTIC
NO SQL
BEGIN
    IF p_n > 0 THEN
        RETURN p_n;
    END IF;
    -- 少了 p_n <= 0 的返回
END;

SELECT fn_bad(0);
-- ERROR 1323 (HY000): FUNCTION fn_bad ended without RETURN
```

`RETURN` 会**立即结束函数**，后面的语句不再执行：

```sql
BEGIN
    IF p_n < 0 THEN
        RETURN 0;          -- 直接返回，下面的 WHILE 不会跑
    END IF;

    WHILE ... DO
        ...
    END WHILE;

    RETURN v_result;
END
```

> [!failure] 常见写法：只在 `IF` 分支里 `RETURN`
> 编译器不会在创建时拦住你，只有运行到"没有返回"的那条路径才报 `1323`。
> 复杂函数建议**单一出口**：所有分支只给结果变量赋值，最后统一 `RETURN v_result;`。

### 5.3 函数不允许递归

```sql
-- 调用自己会报错
SELECT fn_factorial(5);
-- ERROR 1424 (HY000): Recursive stored functions and triggers are not allowed
```

需要递归逻辑，用存储过程（并设置 `max_sp_recursion_depth`），或者在应用层实现。

## 六、函数里不能做什么

这是存储函数和存储过程差异最大的部分，也是报错最集中的地方。

| 限制 | 说明 / 典型错误 |
| --- | --- |
| 不能返回结果集 | 函数体里的 `SELECT` 必须 `INTO`；直接 `SELECT ...` 报 `1415` |
| 不能控制事务 | 不能 `START TRANSACTION` / `COMMIT` / `ROLLBACK`；报 `1422` |
| 不能使用动态 SQL | 不能 `PREPARE` / `EXECUTE` / `DEALLOCATE`；报 `1336` |
| 不能递归 | 报 `1424` |
| 不能改"外层语句正在用"的表 | 报 `1442` |
| 不能用于 `CHECK` 约束 | 8.0.16+ 的 `CHECK` 表达式不允许调用存储函数 |
| 不能用于生成列 | 生成列表达式不允许调用存储函数 |
| 不能用于函数索引 | 索引表达式不允许调用存储函数 |

### 6.1 不能返回结果集

```sql
CREATE FUNCTION fn_bad()
RETURNS INT
DETERMINISTIC
NO SQL
BEGIN
    SELECT id FROM emp;      -- 错误：这是结果集，不是返回值
    RETURN 1;
END;
-- ERROR 1415 (0A000): Not allowed to return a result set from a function
```

函数的 `SELECT` 必须把结果装进变量：

```sql
SELECT COUNT(*) INTO v_cnt FROM emp;
```

### 6.2 不能控制事务

```sql
CREATE FUNCTION fn_bad()
RETURNS INT
MODIFIES SQL DATA
BEGIN
    COMMIT;                  -- 错误
    RETURN 1;
END;
-- ERROR 1422 (HY000): Explicit or implicit commit is not allowed in stored function or trigger
```

函数是被外层 SQL 调用的，外层语句本身可能就在事务里；允许函数随意提交会破坏事务边界。事务逻辑放存储过程。

### 6.3 不能动态 SQL

```sql
PREPARE stmt FROM @sql;      -- 函数里不允许
EXECUTE stmt;
```

动态 SQL 只允许出现在存储过程中。函数需要"按参数变表名/列名"时，通常说明设计方向错了。

### 6.4 不能修改正在被外层语句使用的表

```sql
CREATE FUNCTION fn_bump(p_id INT)
RETURNS INT
MODIFIES SQL DATA
BEGIN
    UPDATE emp SET salary = salary + 1 WHERE id = p_id;
    RETURN 1;
END;

SELECT fn_bump(1) FROM emp;
-- ERROR 1442 (HY000): Can't update table 'emp' in stored function/trigger
-- because it is already used by statement which invoked this stored function/trigger
```

外层 `SELECT` 正在读 `emp`，函数里又去写 `emp`，MySQL 直接拒绝。这不是"加个 `LIMIT` 就能绕过"的问题，而是执行模型不允许。

### 6.5 不能用于 `CHECK`、生成列、函数索引

```sql
-- CHECK 约束：不允许调用存储函数
ALTER TABLE emp
  ADD CONSTRAINT chk_level CHECK (fn_salary_level(salary) IN ('高', '中', '低'));
-- 报错

-- 生成列：不允许调用存储函数
ALTER TABLE emp
  ADD COLUMN salary_level VARCHAR(10)
  GENERATED ALWAYS AS (fn_salary_level(salary)) STORED;
-- 报错

-- 函数索引：表达式里不允许存储函数
CREATE INDEX idx_level ON emp ((fn_salary_level(salary)));
-- 报错
```

这三处都要求表达式**只使用内置函数**。想把"档位"变成可索引的列，只能用内置表达式重写：

```sql
ALTER TABLE emp
  ADD COLUMN salary_level VARCHAR(10)
  GENERATED ALWAYS AS (
      CASE
          WHEN salary >= 12000 THEN '高'
          WHEN salary >= 8000  THEN '中'
          ELSE '低'
      END
  ) STORED;

CREATE INDEX idx_emp_level ON emp (salary_level);

SELECT * FROM emp WHERE salary_level = '高';   -- 能走索引
```

> [!tip] 记住一句话
> **存储函数可以"算"，但不能"建结构"**。凡是要求确定性表达式的地方（`CHECK`、生成列、函数索引），都只认内置函数。

## 七、调用场景与性能

### 7.1 函数会出现在哪里

| 位置 | 示例 |
| --- | --- |
| `SELECT` 列表 | `SELECT fn_salary_level(salary) FROM emp;` |
| `WHERE` | `WHERE fn_salary_level(salary) = '高'` |
| `ORDER BY` | `ORDER BY fn_annual_salary(salary)` |
| `GROUP BY` / `HAVING` | `GROUP BY fn_salary_level(salary)` |
| `JOIN ... ON` | `ON fn_norm(a.name) = fn_norm(b.name)` |
| `UPDATE ... SET` | `SET salary = fn_next(salary)` |
| `INSERT ... VALUES` | `VALUES (fn_next(...))` |

### 7.2 套在索引列上 = 索引失效

```sql
-- 全表扫描：每一行都要先算函数，再比较
SELECT * FROM emp WHERE fn_salary_level(salary) = '高';

-- 改写：直接比较原始列，能走 salary 上的索引
SELECT * FROM emp WHERE salary >= 12000;
```

优化器无法把"函数结果"反推成"列的范围"，除非你建了对应的生成列/函数索引（而这两者又不允许存储函数）。所以：

> [!danger] `WHERE 函数(索引列) = ...` 是最常见的性能事故
> 函数参数是列时，函数必须**逐行执行**，索引直接作废。
> 要么把逻辑改写成对原始列的区间/等值条件，要么用内置表达式建生成列。

### 7.3 逐行调用的成本

```sql
SELECT name, fn_dept_avg(dept) FROM emp;
```

看起来只调用 8 次，但每行都要进入函数、执行一条 `SELECT AVG(...)`。数据量一大就是典型的 N+1：

```sql
-- 集合写法：一次分组算完
SELECT e.name, d.avg_salary
FROM emp e
JOIN (SELECT dept, AVG(salary) AS avg_salary FROM emp GROUP BY dept) d
  ON e.dept = d.dept;
```

> [!warning] 函数没有结果缓存
> MySQL 8 没有"函数结果缓存"这种东西。`fn_dept_avg('研发部')` 在一条语句里出现 100 次，就可能查 100 次表。
> 参数是常量时优化器可能做常量折叠，但这只对纯确定性函数有意义；依赖表数据的函数不要指望。

### 7.4 什么时候函数真的划算

- 逻辑是**纯计算**（格式化、脱敏、等级映射），不碰表。
- 表达式很复杂但复用频繁，命名后显著提升可读性。
- 数据量不大，或函数只作用在结果集很小的查询上。
- 需要在 `ORDER BY` / `GROUP BY` 里复用同一套计算口径。

## 八、管理与查看

```sql
-- 列出当前库的函数
SHOW FUNCTION STATUS WHERE Db = DATABASE();

-- 查看定义
SHOW CREATE FUNCTION fn_salary_level\G

-- 数据字典
SELECT ROUTINE_NAME,
       DTD_IDENTIFIER        AS 返回类型,
       IS_DETERMINISTIC,
       SQL_DATA_ACCESS,
       SECURITY_TYPE
FROM information_schema.ROUTINES
WHERE ROUTINE_SCHEMA = DATABASE()
  AND ROUTINE_TYPE = 'FUNCTION';

-- 只改特征，不改函数体
ALTER FUNCTION fn_salary_level COMMENT '薪资档位：高/中/低';

-- 删除
DROP FUNCTION IF EXISTS fn_salary_level;
```

> [!warning] `ALTER FUNCTION` 改不了函数体
> 它只能改 `COMMENT`、`SQL SECURITY` 等特征，**不能改参数、返回类型和 `BEGIN...END` 里的逻辑**。
> MySQL 也没有 `CREATE OR REPLACE FUNCTION`，改逻辑只能 `DROP` + `CREATE`。
> 注意：**删除函数会连同它的授权一起丢掉**，重建后要重新 `GRANT EXECUTE`。

> [!danger] `DEFINER` 账号被删，函数会报 1449
> ```sql
> -- ERROR 1449 (HY000): The user specified as a definer ('old_user'@'%') does not exist
> ```
> 用 `SHOW CREATE FUNCTION` 看 `DEFINER`，必要时 `ALTER FUNCTION ... SQL SECURITY INVOKER` 或重建。

### 8.1 权限

| 权限 | 用途 |
| --- | --- |
| `CREATE ROUTINE` | 创建函数 |
| `ALTER ROUTINE` | 修改特征、删除函数 |
| `EXECUTE` | 调用函数 |

```sql
GRANT CREATE ROUTINE, ALTER ROUTINE ON demo.* TO 'dev'@'%';
GRANT EXECUTE ON FUNCTION demo.fn_salary_level TO 'app'@'%';
```

### 8.2 不要和内置函数重名

```sql
CREATE FUNCTION abs(x INT) RETURNS INT ...;   -- 不推荐
```

和内置函数同名时，未限定的 `abs(...)` 会解析到内置函数，必须写成 `库名.abs(...)` 才能调用你的版本。命名统一加业务前缀（`fn_`、`biz_`），别去碰 `abs`、`round`、`date` 这些名字。

## 九、常见错误合集

> [!failure] 坑一：`RETURNS` / `RETURN` 写反或漏写
> `CREATE FUNCTION` 必须有 `RETURNS type`；函数体必须有 `RETURN value`。

> [!failure] 坑二：某条路径没有 `RETURN`
> 运行时才报 `ERROR 1323: FUNCTION ... ended without RETURN`。复杂分支用"单一出口"写法。

> [!failure] 坑三：开了 binlog 却没写特征声明
> `ERROR 1418`。按函数实际行为补 `DETERMINISTIC` / `NO SQL` / `READS SQL DATA`，不要第一反应就开 `log_bin_trust_function_creators`。

> [!failure] 坑四：乱标 `DETERMINISTIC`
> 读了表、用了 `NOW()` / `RAND()` 却标确定性，语句级复制下主从可能不一致。

> [!failure] 坑五：函数里直接 `SELECT` 不写 `INTO`
> `ERROR 1415: Not allowed to return a result set from a function`。

> [!failure] 坑六：函数里写 `COMMIT` / `ROLLBACK`
> `ERROR 1422`。事务逻辑放存储过程。

> [!failure] 坑七：函数里用动态 SQL
> `PREPARE` / `EXECUTE` 不允许出现在函数里，报 `1336`。

> [!failure] 坑八：函数里 `UPDATE` 外层正在查的表
> `ERROR 1442`。函数应只读；写操作换过程。

> [!failure] 坑九：在 `CHECK` / 生成列 / 函数索引里调用存储函数
> 都不允许。改用内置表达式，或把校验逻辑放到应用层。

> [!failure] 坑十：`WHERE fn(索引列) = ...`
> 索引失效，全表扫描 + 逐行调用。改写成原始列的区间条件，或用内置表达式的生成列。

> [!failure] 坑十一：参数名和列名同名
> `WHERE dept = dept` 恒真。统一 `p_` / `v_` 前缀。

> [!failure] 坑十二：返回类型太小
> `DECIMAL(10,2)` 装千万级金额、`INT` 装累计计数，可能截断或溢出。金额用 `DECIMAL`，计数用 `BIGINT`。

> [!failure] 坑十三：和内置函数重名
> 不限定库名时调用到的是内置版本。加业务前缀，避免踩名。

## 十、速查表

| 需求 | 写法 |
| --- | --- |
| 创建函数 | `CREATE FUNCTION f(p INT) RETURNS INT ... RETURN ...` |
| 修改分隔符 | `DELIMITER //` … `DELIMITER ;` |
| 纯计算声明 | `DETERMINISTIC NO SQL` |
| 读表声明 | `READS SQL DATA` |
| 写数据声明 | `MODIFIES SQL DATA`（不推荐） |
| 执行身份 | `SQL SECURITY DEFINER` / `INVOKER` |
| 调用 | `SELECT f(1);` / `WHERE f(col) = ...` |
| 局部变量 | `DECLARE v_x INT DEFAULT 0;` |
| 查询赋值 | `SELECT ... INTO v_x FROM ...;` |
| 条件 | `IF ... THEN ... ELSEIF ... ELSE ... END IF;` |
| 多分支 | `CASE ... WHEN ... THEN ... END CASE;` |
| 循环 | `LOOP` / `WHILE` / `REPEAT` |
| 返回 | `RETURN value;` |
| 查看定义 | `SHOW CREATE FUNCTION f\G` |
| 查看列表 | `SHOW FUNCTION STATUS WHERE Db = DATABASE();` |
| 删除 | `DROP FUNCTION IF EXISTS f;` |
| 授权调用 | `GRANT EXECUTE ON FUNCTION db.f TO 'app'@'%';` |
| 检查 binlog | `SELECT @@log_bin, @@log_bin_trust_function_creators;` |

> [!question] 自测三连
> 1. `RETURNS` 和 `RETURN` 各是什么？函数少写 `RETURN` 会在什么时候报错、报什么错？
> 2. 为什么函数里不能 `COMMIT`？函数里写 `SELECT id FROM emp;` 而不加 `INTO` 会怎样？
> 3. 开了 binlog 后创建函数报 `1418`，应该先改什么？为什么不建议直接 `SET GLOBAL log_bin_trust_function_creators = 1`？

---

> [!quote] 一句话记忆
> **`RETURNS` 定类型、`RETURN` 给值、每条路径都要能返回**；**函数只读、单值、能进表达式，不能事务 / 结果集 / 动态 SQL / 递归**；**`DETERMINISTIC` 是承诺不是缓存**；**开 binlog 先写对特征声明，别乱开 trust**；**函数套在索引列上必然失去索引，`CHECK` / 生成列 / 函数索引也都不认存储函数**。
