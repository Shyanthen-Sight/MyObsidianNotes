

> 只写「怎么想」，不写具体语句。三道题分别从「可用手段 → 关键决策 → 易错点 → 自检」四个角度展开。

## 题 1：分数成绩 → 等级成绩

### 先想清楚三件事

1. **分数从哪来**：直接写字面值 / 会话变量 / 表里的列 / 存储过程参数。来源不同，代码所在的层级不同（表达式级 vs 存储程序级）。
2. **用哪一层分支**：
   - SQL 表达式层：`CASE` 表达式（以及 `IF()` 函数）——可以嵌在 `SELECT` 里，不需要建存储程序。
   - 存储程序层：`IF ... ELSEIF ... ELSE ... END IF`——必须放在存储过程 / 函数 / 触发器里。
   实验要求「分支语句」，两种都算分支。先决定做哪一种，再决定要不要建 procedure / function。
3. **输出形式**：只是打印一行结果，还是要返回一个「等级」值给别的语句复用（后者倾向写成函数）。

### 关键决策：区间怎么切

- 题干说「90 分以上」「80 到 90 之间」，边界其实是模糊的：**90 分算优秀还是良好？80、70、60 同理**。这是本题第一个要想清楚的问题。
- 建议按「从高到低、每档用 `>=` 下界」的半开区间思路：`[90,100]`、`[80,90)`、`[70,80)`、`[60,70)`、`[0,60)`。这样每个分数只落进一档，既不重叠也不遗漏。
- 分支是「顺序判断、先命中先返回」，所以**条件的先后顺序本身就是逻辑的一部分**——宽的写前面还是窄的写前面，结果会不一样，想清楚再排。
- 分数有没有上下限（>100、负数）？要不要单独兜底？

### 易错点清单

- `BETWEEN` 是闭区间，相邻两档会在边界值上重复命中，只能靠顺序「抢」结果——要么避开 `BETWEEN`，要么明确顺序。
- `NULL` 分数会落进 `ELSE` 分支，想好它算「不及格」还是「未知」。
- 分数是小数（如 90.5）时，`>=` 与 `>` 的选择会改变结果。
- `IF()` 函数只有真/假两路，多档必须嵌套，可读性差；多档判断优先考虑 `CASE`。
- 存储程序里 `DECLARE` 必须放在块的开头，作用域只在该 `BEGIN...END` 内。
- 结果列起个有意义的别名（如「等级」），截图更清楚。

### 自检方法

- 用边界值逐个测：100、90、89、80、79、70、69、60、59、0。
- 问自己：90 分落在哪一档，和题干「80 到 90 之间」是否自洽？**把采用的假设写进实验报告**，这本身就是得分点。

## 题 2：1 到 100 求和

### 先想清楚「1 到 100 从哪来」

MySQL 没有现成的「生成 1..N」函数（8.0 可用递归 CTE 自己造；某些分支/MariaDB 有序列函数）。可选路线：

1. **递归 CTE**：先给出起点行，再写「上一行 +1 且不超过 100」的递推，最后对结果集求和。重点是想清楚递归的**终止条件写在哪**。
2. **存储过程 + 循环**（`WHILE` / `REPEAT` / `LOOP`）：需要一个累加变量 + 一个计数器，循环体内「累加、自增」，循环外输出。
3. **建一张数字表**再聚合——最「SQL」但最麻烦，通常不作为首选。

### 关键决策

- **累加变量放哪**：存储过程里用 `DECLARE` 局部变量，还是会话级 `@变量`？两者作用域不同，报告里要说明。
- **初始值**：累加器从 0 开始、计数器从 1 开始——两个都要初始化，漏一个结果就错。
- **终止条件**：`<= 100` 还是 `< 100`？想清楚最后一次循环加的是 100 还是 99。
- 若走递归 CTE：默认递归深度上限（`cte_max_recursion_depth`）够不够？本题 100 层没问题，但要意识到这个限制存在。
- 数学公式 `n(n+1)/2` 只能当**验算器**，不能当实现，否则就失去了练循环的意义。

### 易错点

- `SELECT` 里不能直接写循环——循环属于存储程序，必须先建 procedure，注意 `DELIMITER` 的切换。
- 变量未初始化时是 `NULL`，而 `NULL + 任何数 = NULL`，最终结果会是 `NULL` 而不是报错（很隐蔽）。
- 循环变量在循环外是否可见、是否被意外重置。

### 自检方法

- 用公式独立算一遍作为标准答案对比。
- 再测小范围（如 1..10）验证循环边界。

## 题 3：10 的阶乘

### 思路与题 2 同构，但有三处不同

1. **累加 → 累乘**：初始值必须是 1（乘法的单位元），从 0 开始会永远得 0。
2. **数据类型量级**：阶乘增长极快，10! 本身还在 INT 范围内，但再大几阶就会溢出。写之前先想「结果会不会超出变量/列的容量」，必要时选 `BIGINT` 或 `DECIMAL`。
3. **递推关系**：`f(n) = n × f(n-1)`，递归 CTE 的锚点和步进都要体现「乘」而不是「加」。

### 三条路线同样适用

- **递归 CTE**：锚点给 `1! = 1`，递推时 n 增 1、积乘 n，直到 n 到 10。
- **存储过程 + `WHILE`**：同题 2，只把「加」换成「乘」。
- **会话变量 + `SELECT`**：不用建存储程序，但可读性差，报告里要说明原理。

### 易错点

- 初值写成 0（乘出来恒为 0）。
- 计数器与乘数混淆：这一步是「乘 n」还是「乘 n-1」。
- 起算口径：从 1! 还是从 0! 开始（0! = 1 的定义问题）。
- 溢出：即使 10! 不溢出，也应在报告里提一句「更大的 n 需要更宽的类型」。

### 自检方法

- 小值验证：1! = 1、2! = 2、3! = 6、4! = 24、5! = 120。
- 与手算 / 计算器结果对照。

## 贯穿三题的通用提醒

- 三题练的是同一类能力：题 1 是**选择结构**，题 2、3 是**循环结构**。报告按这个分类叙述会更清晰。
- 脚本加注释，并附「输入 → 期望输出 → 实际输出」的对照表。
- 建存储程序记得 `DELIMITER` 切换后要恢复；命名避免与系统函数冲突。
- 结果集列名起得有意义的（等级、总和、阶乘）。
