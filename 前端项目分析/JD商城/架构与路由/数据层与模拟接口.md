# 数据层与模拟接口

> [!abstract] 一句话
> `src/api/goods.js` 是项目的**唯一数据入口**：它在模块加载时把两份 JSON ==归一化成前端字段==（snake_case → camelCase、价格转数字、生成摘要），再用 `setTimeout + Promise` 提供三个「像网络请求」的函数，页面因此可以按真实异步接口的方式书写。

---

## 一、整体结构

```text
database/products.json ─┐
                        ├─ 模块加载时一次性处理
database/comments.json ─┘
        ↓
normalizeProduct(raw)  →  products 数组（只读）
        ↓
fetchGoodsList()   列表：搜索 + 排序 + 分页
fetchGoodsDetail() 详情：按 skuId 查找
fetchComments()    评论：筛选 + 字段转换
formatPrice()      价格：统一保留两位小数
```

文件位于 `src/api/goods.js`，共 120 行。虽然叫 `api`，但**没有任何 HTTP 请求**。

---

## 二、导入原始 JSON

```js
import productsRaw from '../../database/products.json'
import commentsRaw from '../../database/comments.json'
```

- Vite 原生支持导入 `.json`，会把文件内容转成默认导出的 JS 对象。
- `database/` 不在 `src/` 下，所以这里用相对路径 `../../database/` 回到项目根目录。
- 两份 JSON 会在构建时被打进 bundle，因此数据量越大，首屏 JS 越大。当前 61 条商品 + 600 条评论已经使 JS 达到约 1.9 MB（其中主要仍是 Element Plus）。

## 三、字段归一化 `normalizeProduct`

原始数据使用后端常见的下划线命名，页面使用驼峰命名。转换集中在 `normalizeProduct`：

```js
export function normalizeProduct(raw) {
  return {
    ...raw,
    skuId: raw.sku_id,
    price: Number(raw.price),
    shopName: raw.shop_name,
    mainImageUrls: raw.main_image_urls,
    detailImageUrls: raw.detail_image_urls,
    shortInfo: Object.values(raw.params || {}).slice(0, 3).join(' · '),
  }
}

const products = productsRaw.map(normalizeProduct)
```

字段对应关系：

| 原始字段 | 前端字段 | 处理 |
| --- | --- | --- |
| `sku_id` | `skuId` | 直接重命名 |
| `price` | `price` | `Number()` 转数字 |
| `shop_name` | `shopName` | 直接重命名 |
| `main_image_urls` | `mainImageUrls` | 直接重命名 |
| `detail_image_urls` | `detailImageUrls` | 直接重命名 |
| `params` | `shortInfo` | 取前 3 个参数值，用 ` · ` 连接 |

### 3.1 为什么要归一化

1. **页面组件不需要知道后端字段长什么样。** 组件只认 `skuId`、`price`、`shopName`。
2. **类型统一。** 原始 `price` 是字符串（如 `"1319"`），归一化后是数字，可以直接排序、相乘、格式化。
3. **补充派生字段。** `shortInfo` 不是原始数据，而是为购物车和卡片摘要生成的。

> [!note] `...raw` 保留了原始字段
> 归一化对象中同时存在 `sku_id` 和 `skuId`、`shop_name` 和 `shopName`。这不会影响功能，但会让对象变「胖」。更干净的做法是只挑选需要的字段，或删除下划线字段。

### 3.2 `shortInfo` 的一个小问题

```js
Object.values(raw.params || {}).slice(0, 3).join(' · ')
```

`Object.values` 的顺序遵循对象键的插入顺序，因此取到的是**参数对象里的前三个值**，不一定是「品牌 / 型号 / 屏幕」这类最有代表性的规格。不同商品的参数键顺序不同，摘要的语义因此不稳定。

## 四、商品列表接口 `fetchGoodsList`

```js
export function fetchGoodsList({
  keyword = '',
  page = 1,
  pageSize = 12,
  sort = 'default',
} = {}) {
  const searchKeyword = keyword.trim().toLowerCase()

  let result = products.filter((product) => {
    if (!searchKeyword) return true

    const searchableText = [
      product.title,
      product.brand,
      product.shopName,
      ...Object.values(product.params || {}),
    ]
      .join(' ')
      .toLowerCase()

    return searchableText.includes(searchKeyword)
  })

  if (sort === 'price-asc') {
    result.sort((a, b) => a.price - b.price)
  } else if (sort === 'price-desc') {
    result.sort((a, b) => b.price - a.price)
  }

  const start = (page - 1) * pageSize
  const list = result.slice(start, start + pageSize)

  return new Promise((resolve) => {
    setTimeout(() => {
      resolve({ list, total: result.length })
    }, 150)
  })
}
```

执行顺序：

```text
products（61 条）
  ↓ filter：关键字匹配
  ↓ sort：价格升/降序（可选）
  ↓ slice：截取当前页
  ↓ Promise + setTimeout(150ms)
{ list, total }
```

### 4.1 搜索匹配范围

| 字段 | 是否参与匹配 |
| --- | --- |
| `title` | ✅ |
| `brand` | ✅ |
| `shopName` | ✅ |
| `params` 的所有值 | ✅ |
| `skuId` | ❌ |
| `shop_name` 原字段 | ❌（但 `shopName` 已包含） |

所有文本先 `join(' ')` 再 `toLowerCase()`，实现不区分大小写的包含匹配。中文没有大小写，但英文品牌名（如 `SK-II`、`OPPO`）可以匹配。

> [!tip] 为什么先 `join` 再 `includes`
> `includes` 对单个字段调用会产生「跨字段误匹配」之外的问题较少，但 `join` 后一次匹配更简单，也能匹配到跨字段的连续文本（实际很少发生）。主要优点是代码短。

### 4.2 排序参数目前没有入口

`sort` 支持 `price-asc` / `price-desc`，但 `goods-list.vue` 调用时**没有传 `sort`**：

```js
const result = await fetchGoodsList({
  keyword: String(route.query.keyword || ''),
  page: currentPage.value,
  pageSize,
})
```

因此排序能力是「已实现但未接入 UI」的。若要启用，需要在列表页加一个排序下拉框，并把这个值传进来。

### 4.3 分页计算

```js
const start = (page - 1) * pageSize
const list = result.slice(start, start + pageSize)
```

- 第 1 页：`0 – 11`
- 第 2 页：`12 – 23`
- 第 6 页：`60 – 70`（实际只有第 61 条）

`total` 返回的是**过滤后的总数**，不是当前页条数。页面据此计算总页数：

```js
const totalPages = computed(() => Math.ceil(total.value / pageSize))
```

61 条、每页 12 条 → `Math.ceil(61 / 12) = 6` 页。

> [!warning] 页码越界没有在数据层处理
> 如果请求 `page = 99`，`slice` 会返回空数组，但 `total` 仍为 61。页面层依靠 `goToPage` 的边界判断来避免这种情况。更稳妥的做法是在数据层把 `page` 限制在 `1..totalPages`。

### 4.4 为什么用 `setTimeout` 模拟异步

```js
return new Promise((resolve) => {
  setTimeout(() => {
    resolve({ list, total: result.length })
  }, 150)
})
```

目的：

1. 让页面中的 `loading` 状态有机会显示。
2. 让调用方必须使用 `await` / `.then`，与真实接口保持一致。
3. 将来替换成 `axios.get('/api/products', { params })` 时，页面代码几乎不用改。

> [!note] 这不是真正的并发问题
> 数据在本地同步算完，只是延迟返回。因此不存在真实网络中的超时、失败、取消。也正因如此，`fetchGoodsList` 永远不会 `reject`。

## 五、商品详情接口

```js
export function fetchGoodsDetail(skuId) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      const product = products.find((item) => item.skuId === skuId)
      if (!product) {
        reject(new Error('商品不存在'))
        return
      }
      resolve(product)
    }, 200)
  })
}
```

- 用 `find` 按 `skuId` 查找。
- 找不到时 `reject`，页面捕获后显示「商品不存在或加载失败」。
- 延迟 200ms，比列表稍长，模拟「详情请求更重」。

> [!warning] 严格相等比较
> `item.skuId === skuId` 要求两者都是字符串。路由参数 `props.skuId` 是字符串，归一化时 `skuId` 来自 JSON 字符串，类型一致。如果将来把 `skuId` 转成数字，这里会全部查找失败。

## 六、评论接口

```js
export function fetchComments(skuId) {
  return new Promise((resolve) => {
    setTimeout(() => {
      const comments = commentsRaw
        .filter((comment) => comment.sku_id === skuId)
        .map((comment) => ({
          nickname: comment.user_nickname,
          avatar: comment.user_avatar_url,
          content: comment.content,
          after: comment.after_content,
          images: comment.images_urls,
          time: comment.comment_time,
        }))
      resolve(comments)
    }, 150)
  })
}
```

字段转换：

| 原始字段 | 组件字段 |
| --- | --- |
| `user_nickname` | `nickname` |
| `user_avatar_url` | `avatar` |
| `content` | `content` |
| `after_content` | `after` |
| `images_urls` | `images` |
| `comment_time` | `time` |

注意：

- 过滤掉 `comment_id`、`score`、`sku_id` 等字段。
- `comment_id` 被丢弃后，组件失去了稳定的唯一键，只能用 `nickname + time` 拼 key，导致 127 组重复，详见 [[商品详情组件]]。
- `score` 全是 `null`，即使保留也无法展示评分。
- `images` 直接取 `images_urls`，如果某条数据缺少该字段，组件里的 `comment.images.length` 会报错。当前数据全部有数组，但这是**对数据结构的强假设**。

## 七、价格格式化 `formatPrice`

```js
export function formatPrice(value) {
  const price = Number(value)
  if (!Number.isFinite(price)) {
    return '0.00'
  }
  return price.toFixed(2)
}
```

用途：

- 商品卡片：`¥{{ formatPrice(product.price) }}`
- 详情页：`¥{{ formatPrice(product.price) }}`
- 购物车单价 / 小计 / 合计

设计要点：

1. **统一入口**：所有金额展示都走这个函数，避免每个组件各写一套。
2. **容错**：`Number('abc')` 得到 `NaN`，`Number.isFinite` 判断后返回 `'0.00'`，不会显示 `NaN`。
3. **两位小数**：`toFixed(2)` 保证 `1319` 显示为 `1319.00`。

> [!note] `toFixed` 的舍入
> `toFixed` 使用二进制浮点近似，个别边界值（如 `1.005`）可能出现 `1.00` 而不是 `1.01`。电商场景若要求严格金额精度，应使用整数分或专门的金额库。当前项目价格多为整数，影响不大。

## 八、数据层评价

### 8.1 优点

- 字段转换集中在一个函数，页面只面对统一模型。
- 列表查询把「搜索 → 排序 → 分页」封装在一个函数里，页面逻辑简单。
- 用 Promise 模拟异步，保留了未来接真实后端的接口形状。
- 价格格式化有容错。

### 8.2 可改进点

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| `sort` 未接入 UI | 能力闲置 | 列表页加排序控件 |
| 评论丢弃 `comment_id` | 列表 key 不稳定 | 保留 `id` 字段 |
| `images` 未做默认值 | 缺字段时运行时报错 | `images: comment.images_urls || []` |
| `mainImageUrls` 未做默认值 | 缺图时模板报错 | 归一化时补 `[]` |
| 页码不设边界 | 空页 | 数据层 clamp |
| 无请求失败/取消 | 无法处理真实网络 | 接真实 API 时补 `AbortController` |
| 全量 JSON 进 bundle | 体积增大 | 大数据改后端接口或分文件懒加载 |

> [!tip] 接真实后端的替换方式
> 保持三个函数的**入参与返回结构不变**，只把内部实现换成 `fetch` / `axios`：
>
> ```js
> export async function fetchGoodsList(params) {
>   const { data } = await axios.get('/api/products', { params })
>   return data   // 仍然返回 { list, total }
> }
> ```
>
> 页面层不需要改动，这正是这层抽象的价值。
