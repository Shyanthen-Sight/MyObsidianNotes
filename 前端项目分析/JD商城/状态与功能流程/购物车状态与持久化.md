# 购物车状态与持久化

> [!abstract] 一句话
> `src/stores/cart.js` 用**模块级单例**实现了一个迷你 store：顶层 `reactive({ items })` 保存购物车，`computed` 派生件数与金额，`watch(..., { deep: true })` 在每次变化后把白名单字段写进 ==localStorage（键 `jd_cart_v1`）==；所有组件通过 `useCart()` 拿到同一份状态和方法。

---

## 一、为什么需要独立的状态模块

购物车数据要被多个互不相邻的组件同时使用：

```text
GoodsInfoPanel（详情页）  → 写入：加入购物车
CartDot（顶部导航）        → 读取：角标件数
CartItem（购物车页）       → 读写：数量、删除
FooterFixed（结算栏）      → 读取：总件数、总金额
Cart（购物车页）           → 读取：商品数组
```

如果靠 props 传递，需要从 `App` 一路传到每个组件，非常繁琐。因此项目把状态抽到 `stores/cart.js`。

> [!note] 它其实就是「没有 Pinia 的 Pinia」
> `useCart()` 的模式与 Pinia 的 setup store 非常像：模块顶层创建状态，导出一个函数返回状态和操作。区别是没有 `defineStore`、没有 devtools 集成、没有 SSR 支持。

## 二、模块级单例

```js
import { reactive, computed, watch } from 'vue'

const state = reactive({
  items: [],
})
```

关键点：`state` 定义在**模块顶层**，而不是 `useCart()` 内部。

```js
// 错误示范：每次调用都创建新对象
export function useCart() {
  const state = reactive({ items: [] })  // ❌ 不共享
}

// 正确：模块只执行一次，state 只有一份
const state = reactive({ items: [] })
export function useCart() {
  return { items: state.items }          // ✅ 共享
}
```

ES Module 在同一页面生命周期内只会执行一次，因此：

```text
第一次 import './stores/cart'
  → 创建 state
  → 读取 localStorage
  → 注册 watch
  → 导出 useCart

之后所有 import 都复用同一模块实例
```

这就是跨组件共享的根本原因。

## 三、初始化：从 localStorage 恢复

```js
const STORAGE_KEY = 'jd_cart_v1'

try {
  const savedItems = JSON.parse(localStorage.getItem(STORAGE_KEY) || '[]')

  if (Array.isArray(savedItems)) {
    state.items.push(
      ...savedItems.filter(
        (item) =>
          item &&
          typeof item.skuId === 'string' &&
          typeof item.title === 'string' &&
          typeof item.price === 'number' &&
          Number.isFinite(item.price) &&
          typeof item.count === 'number' &&
          item.count >= 1 &&
          item.count <= 99,
      ),
    )
  }
} catch (error) {
  console.error('读取购物车数据失败：', error)
}
```

### 3.1 校验规则

| 字段 | 规则 | 目的 |
| --- | --- | --- |
| `item` 本身 | 真值 | 过滤 `null` |
| `skuId` | `string` | 保证能作为主键 |
| `title` | `string` | 保证能渲染 |
| `price` | `number` 且有限 | 防止 `NaN` / `Infinity` 污染金额 |
| `count` | `number` 且 1–99 | 防止非法数量 |

### 3.2 为什么需要校验

`localStorage` 是用户可编辑的，也可能是旧版本遗留数据。直接信任会导致：

- `price: "abc"` → 合计显示 `NaN`
- `count: -5` → 负数量
- `item: null` → 模板报错
- 非数组 JSON → `.filter` 报错

`try/catch` 还能兜住 `JSON.parse` 的语法错误（用户手动改坏了存储）。

### 3.3 校验的缺口

1. **没有校验 `cover`**：如果旧数据缺少 `cover`，购物车图片会显示破图。
2. **没有校验 `shortInfo`**：缺失时模板显示空白，不致命。
3. **没有去重**：如果存储中有两个相同 `skuId`，会原样恢复成两行。`add` 和 `setCount` 都只操作 `find` 到的第一项，第二项会变成「幽灵行」。
4. **没有校验数量是否整数**：`1.5` 会通过 `>=1 && <=99`。
5. **没有限制数组长度**：理论上可以塞入大量数据，拖慢渲染。

更严格的写法：

```js
const clean = savedItems.filter(isValidItem).map((item) => ({
  skuId: item.skuId,
  title: item.title,
  cover: typeof item.cover === 'string' ? item.cover : '',
  price: item.price,
  shortInfo: typeof item.shortInfo === 'string' ? item.shortInfo : '',
  count: Math.min(Math.max(Math.floor(item.count), 1), 99),
}))

// 按 skuId 去重
const unique = [...new Map(clean.map((item) => [item.skuId, item])).values()]
state.items.push(...unique)
```

## 四、持久化：深度 `watch`

```js
watch(
  state,
  (newState) => {
    const items = newState.items.map((item) => ({
      skuId: item.skuId,
      title: item.title,
      cover: item.cover,
      price: item.price,
      shortInfo: item.shortInfo,
      count: item.count,
    }))

    localStorage.setItem(STORAGE_KEY, JSON.stringify(items))
  },
  { deep: true },
)
```

### 4.1 监听方式

```js
watch(state, callback, { deep: true })
```

- `state` 是 `reactive` 对象，`watch` 会追踪它的属性。
- `deep: true` 确保 `state.items` 数组内部元素的 `count` 变化也能触发。
- 没有 `immediate: true`，所以初始化读取时不会立刻写回。

### 4.2 为什么要重新 `map` 一遍

`state.items` 中的对象只包含：

```js
{
  skuId, title, cover, price, shortInfo, count
}
```

理论上可以直接 `JSON.stringify(newState.items)`。重新映射的作用是**白名单**：

- 防止未来给 item 添加临时字段（如 `selected`、`loading`）后被持久化。
- 保证存储结构稳定。

### 4.3 写入时机

```text
add() / remove() / setCount() / clear()
  ↓ 修改 state.items
watch 回调（异步，默认 flush: 'pre'）
  ↓
localStorage.setItem
```

`watch` 的回调默认在组件更新前批量执行，因此连续修改多次只会写一次（同一 tick 内合并）。

### 4.4 潜在问题

| 问题 | 说明 | 建议 |
| --- | --- | --- |
| 写入没有 `try/catch` | 隐私模式 / 配额满时 `setItem` 会抛错 | 包一层 try/catch |
| 没有跨标签页同步 | A 标签页加购，B 标签页不更新 | 监听 `window.storage` 事件 |
| 每次修改都全量序列化 | 数据大时略耗性能 | 当前规模无影响 |
| 存储键带版本号 | `jd_cart_v1`，升级结构时旧数据不会自动迁移 | 写迁移逻辑或换 key |

跨标签页同步示意：

```js
window.addEventListener('storage', (event) => {
  if (event.key !== STORAGE_KEY || !event.newValue) return
  const items = JSON.parse(event.newValue)
  state.items.splice(0, state.items.length, ...items)
})
```

## 五、派生状态 `computed`

### 5.1 总件数

```js
const totalCount = computed(() => {
  return state.items.reduce((total, item) => total + item.count, 0)
})
```

- 遍历所有条目，累加 `count`。
- 同一商品数量 3，计 3 件。
- 顶部角标、结算栏「共 N 件商品」、结算按钮文字都用它。

### 5.2 总金额

```js
const totalAmount = computed(() => {
  const amount = state.items.reduce((total, item) => {
    return total + item.price * item.count
  }, 0)

  return Number(amount.toFixed(2))
})
```

- 单价 × 数量再求和。
- `toFixed(2)` 处理浮点误差，再 `Number()` 去掉末尾 0。
- 显示时再走 `formatPrice` 补回两位小数。

> [!note] `Number(amount.toFixed(2))` 的意义
> `19.9 * 3 = 59.699999999999996`，`toFixed(2)` 得到 `"59.70"`，`Number` 得到 `59.7`。这样 `totalAmount` 是一个「最多两位小数的数字」，便于继续参与计算和格式化。

### 5.3 商品种数

```js
const kinds = computed(() => state.items.length)
```

统计的是「有几种商品」，不是「共几件」。

> [!warning] `kinds` 目前没有被任何组件使用
> 它被 `return` 出去了，但全项目没有任何地方读取。属于**预留 API**。同理，store 里的 `increase(skuId)` 和 `decrease(skuId)` 也没有被使用——组件里的 `increase` / `decrease` 是各自组件内部的局部函数，不是 store 的。可以删除以减少维护面，或保留作为未来「+ / - 按钮」的快捷方法。

## 六、操作方法

### 6.1 `add(product, count = 1)`

```js
function add(product, count = 1) {
  const existingItem = state.items.find(
    (item) => item.skuId === product.skuId,
  )

  if (existingItem) {
    existingItem.count = Math.min(existingItem.count + count, 99)
    return
  }

  state.items.push({
    skuId: product.skuId,
    title: product.title,
    cover: product.mainImageUrls[0],
    price: product.price,
    shortInfo: product.shortInfo || '',
    count: Math.min(Math.max(count, 1), 99),
  })
}
```

两种情况：

```text
已存在 → 数量累加，上限 99
不存在 → 新建条目，数量限制在 1–99
```

要点：

- **以 `skuId` 为唯一键**，同一商品不会出现两行。
- **只保存快照字段**，不保存整个 `product`，避免把 34 项参数、十几张图片都塞进 localStorage。
- **`cover` 取第一张主图**，依赖 `mainImageUrls` 存在。
- **已存在分支没有下限保护**：如果外部传入负数，`existingItem.count + count` 可能小于 1。UI 只传正数，所以当前安全。

### 6.2 `remove(skuId)`

```js
function remove(skuId) {
  const index = state.items.findIndex((item) => item.skuId === skuId)
  if (index !== -1) {
    state.items.splice(index, 1)
  }
}
```

用 `splice` 而不是重新赋值数组，保持 `items` 的引用不变。

> [!tip] 为什么不用 `filter` 重新赋值
> `Cart` 组件已经把 `items` 数组引用传给 `CartList`。如果执行 `state.items = state.items.filter(...)`，`items` 引用会变，已经解构出来的 `items`（如 `Cart` 中的 `const { items } = useCart()`）仍指向旧数组，界面不会更新。`splice` 原地修改则没有这个问题。

### 6.3 `setCount(skuId, count)`

```js
function setCount(skuId, count) {
  const item = state.items.find((item) => item.skuId === skuId)
  if (!item) return

  if (count <= 0) {
    remove(skuId)
    return
  }

  item.count = Math.min(count, 99)
}
```

规则：

- 找不到商品：静默返回。
- `count <= 0`：删除该商品。
- 否则：上限 99。

`NumAddDel` 永远不会传 0（最少 1），所以删除分支目前只是 API 层的保险。

> [!warning] 没有处理 `NaN` / 非整数
> `Math.min(NaN, 99)` 是 `NaN`。如果调用方传入非法值，`item.count` 会变成 `NaN`，进而污染合计。可以在入口加：
>
> ```js
> const next = Math.floor(Number(count))
> if (!Number.isFinite(next)) return
> ```

### 6.4 `increase` / `decrease`

```js
function increase(skuId) {
  const item = state.items.find((item) => item.skuId === skuId)
  if (item) item.count = Math.min(item.count + 1, 99)
}

function decrease(skuId) {
  const item = state.items.find((item) => item.skuId === skuId)
  if (item && item.count > 1) item.count -= 1
}
```

- 增加：上限 99。
- 减少：下限 1，不会减到 0。
- 目前未被组件使用。

### 6.5 `clear()`

```js
function clear() {
  state.items.splice(0)
}
```

`splice(0)` 删除从索引 0 开始的所有元素，原地清空数组。结算时调用，随后 `watch` 会把空数组写回 localStorage。

## 七、`useCart()` 返回结构

```js
export function useCart() {
  // ...方法定义...

  return {
    items: state.items,
    totalCount,
    totalAmount,
    kinds,
    add,
    remove,
    setCount,
    increase,
    decrease,
    clear,
  }
}
```

| 返回项 | 类型 | 使用方 |
| --- | --- | --- |
| `items` | 响应式数组 | `Cart`、`CartList`、`CartItem` |
| `totalCount` | `ComputedRef<number>` | `CartDot`、`FooterFixed` |
| `totalAmount` | `ComputedRef<number>` | `FooterFixed` |
| `kinds` | `ComputedRef<number>` | 未使用 |
| `add` | 函数 | `GoodsInfoPanel` |
| `remove` | 函数 | `CartItem` |
| `setCount` | 函数 | `CartItem`（重命名为 `updateCount`） |
| `increase` | 函数 | 未使用 |
| `decrease` | 函数 | 未使用 |
| `clear` | 函数 | `FooterFixed` |

> [!note] 解构不会丢失响应性
> `const { totalCount } = useCart()` 拿到的是 `ComputedRef` 对象，模板中自动解包；脚本中需要 `.value`。`const { items } = useCart()` 拿到的是 `reactive` 数组代理，原地修改仍然触发更新。

## 八、完整持久化流程

### 8.1 应用启动

```text
import stores/cart.js
  ↓
state = reactive({ items: [] })
  ↓
localStorage.getItem('jd_cart_v1')
  ↓ JSON.parse
  ↓ Array.isArray? → filter 校验
  ↓ state.items.push(...合法项)
  ↓
watch(state, save, { deep: true }) 注册
```

### 8.2 修改购物车

```text
用户点「加入购物车」
  ↓
add(product, count)
  ↓
state.items 变化
  ↓
Vue 触发依赖它的组件更新（角标、列表、合计）
  ↓
watch 回调执行
  ↓
白名单 map → JSON.stringify → localStorage.setItem
```

### 8.3 刷新页面

```text
页面重新加载
  ↓
模块重新执行
  ↓
从 localStorage 恢复 items
  ↓
购物车数量、金额、角标立即恢复
```

## 九、设计评价

### 9.1 优点

1. **单例清晰**：模块顶层状态，组件无需层层传 props。
2. **读写闭环**：初始化校验 + 深度监听写回。
3. **操作集中**：数量上限、合并规则、删除逻辑都在 store，组件不重复实现。
4. **快照精简**：只存必要字段，localStorage 体积小。
5. **`splice` 保持引用**：避免解构后的数组失联。

### 9.2 风险

| 风险 | 级别 | 说明 |
| --- | --- | --- |
| 写入无异常处理 | 中 | 隐私模式可能抛错 |
| 无跨标签页同步 | 低 | 多开页面时数据不一致 |
| 恢复数据未去重 | 中 | 手动篡改后出现重复行 |
| `NaN` 未防御 | 低 | UI 正常不会触发 |
| 未使用 API | 低 | `kinds` / `increase` / `decrease` |
| 无 Pinia devtools | 低 | 调试体验略差 |

## 十、小结

```text
一份状态：state.items
三个派生：totalCount / totalAmount / kinds
六个操作：add / remove / setCount / increase / decrease / clear
两个生命周期：启动时读 localStorage，变化时写 localStorage
```

如果只能记住一句话：

> **购物车是「模块级单例 + 深度 watch 落盘」，组件只负责触发操作，不负责保存。**
